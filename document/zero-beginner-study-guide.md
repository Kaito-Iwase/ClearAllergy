# ClearAllergy ゼロから学ぶ Web アプリ基礎ガイド

作成日: 2026-04-24 JST

このドキュメントは、ClearAllergy のコードを読む前に、Web アプリ開発の前提知識を身につけるための学習ガイドです。

読む人は、Web アプリ、フロントエンド、バックエンド、HTTP、API、データベース、TypeScript、React、Next.js、認証、Prisma、PostgreSQL、Clerk、Vercel Blob をまだ知らない前提です。

最初から全部を覚える必要はありません。まずは「画面を見る」「ボタンを押す」「データが保存される」という流れを、飲食店の例に置き換えて理解していきます。

## 1. まず、このアプリは何をするものか

ClearAllergy は、飲食店とお客さんの間で、メニューのアレルギー情報をわかりやすく共有するためのアプリです。

飲食店は、自分のお店のメニューを登録します。たとえば、カレー、パスタ、ケーキ、ドリンクなどです。

それぞれのメニューには、名前、説明、価格、写真、そしてアレルゲン情報を入れます。アレルゲンとは、卵、乳、小麦、えび、そば、落花生など、アレルギーの原因になる可能性がある食材のことです。

お客さんは、お店に行く前や注文する前に、スマホやパソコンでメニューを確認できます。

たとえば、お客さんが「卵が入っている料理は避けたい」と思っている場合、ClearAllergy の公開ページを見ることで、どのメニューに卵が含まれているか、どのメニューは卵なしなのかを事前に確認できます。

つまり ClearAllergy は、次のような役割を持つアプリです。

- 飲食店がメニュー情報を登録する
- 飲食店がアレルゲン情報を登録する
- お客さんが公開ページでメニューとアレルゲン情報を見る
- 飲食店だけが管理画面でメニューを追加・編集・削除できる

ここでは、まだ難しい技術名は覚えなくて大丈夫です。

まずは、ClearAllergy は「飲食店のメニュー台帳を、お客さんが見やすい形で公開する仕組み」だと考えてください。

## 2. Webアプリとは何か

Web アプリとは、ブラウザで開いて使うアプリのことです。

ブラウザとは、Web ページを見るためのアプリです。Google Chrome、Safari、Microsoft Edge、Firefox などがブラウザです。

URL とは、Web 上の住所のようなものです。たとえば `https://example.com/shops/abc123` のような文字列です。住所を入力すると家にたどり着くように、URL を開くと特定の画面にたどり着きます。

Web アプリには、大きく分けて「画面を見る側」と「データを処理する側」があります。

飲食店にたとえると、画面を見る側は客席です。お客さんがメニューを見たり、注文したりする場所です。

データを処理する側は厨房です。注文を受け取り、必要な作業をして、料理を出します。

ブラウザでボタンを押すことは、客席から厨房へ注文票を出すことに似ています。

この注文票にあたるものが HTTP リクエストです。HTTP とは、ブラウザとサーバーがやり取りするためのルールです。リクエストとは、ブラウザからサーバーへ送るお願いです。

厨房から料理が返ってくることは、HTTP レスポンスに似ています。レスポンスとは、サーバーからブラウザへ返ってくる結果です。

Web サイトと Web アプリは似ていますが、少し違います。

Web サイトは、情報を見ることが中心です。会社紹介ページ、ニュース記事、店舗案内ページなどです。

Web アプリは、見るだけでなく、入力したり、保存したり、ログインしたり、データを変更したりできます。ネット予約、EC サイト、家計簿アプリ、管理画面などが Web アプリです。

ClearAllergy は Web アプリです。理由は、ただ情報を表示するだけではなく、飲食店がログインしてメニューを作成し、保存し、公開状態を変更し、画像をアップロードできるからです。

## 3. フロントエンドとバックエンドとは何か

フロントエンドとは、ユーザーが見る画面のことです。

ClearAllergy でいうと、お客さんが見る公開ページや、飲食店が使う管理画面がフロントエンドです。

たとえば、次のようなものがフロントエンドです。

- 店舗一覧画面
- 店舗ごとの公開メニュー画面
- メニュー詳細画面
- 管理画面のメニュー一覧
- メニュー作成フォーム
- メニュー編集フォーム
- 保存ボタン
- 画像アップロード欄

バックエンドとは、画面の裏側でデータを処理する部分です。

たとえば、次のような作業がバックエンドです。

- 保存ボタンが押されたら、送られてきたメニュー名を受け取る
- ログインしている飲食店かどうか確認する
- 他のお店のメニューを勝手に編集できないようにする
- データベースにメニューを保存する
- 公開中のメニューだけをお客さんに見せる
- 画像を保存する

ClearAllergy では、API や DB 操作がバックエンドにあたります。

API とは、画面とサーバーがデータをやり取りするための窓口です。DB とは、データベースの略で、アプリのデータを保存する場所です。

初心者が混乱しやすい点があります。

それは、Next.js ではフロントエンドとバックエンドを同じプロジェクトの中に書けるという点です。

普通の説明では「フロントエンドは画面」「バックエンドはサーバー」と分けて言われます。しかし Next.js では、同じ `app` フォルダの中に、画面のファイルと API のファイルが並びます。

たとえば、`page.tsx` は画面を作るファイルです。一方、`route.ts` は API を作るファイルです。

つまり Next.js は、画面だけでなく、API も同じ中に書ける道具です。

ClearAllergy では、公開ページ、管理画面、API が Next.js の中にまとまっています。そのため、1 つのリポジトリの中で「画面」「API」「DB 操作」をまとめて学べます。

## 4. HTTPとAPIとは何か

HTTP とは、ブラウザとサーバーがやり取りするためのルールです。

飲食店で考えると、客席と厨房の間で使う注文ルールのようなものです。

お客さんが店員さんに「カレーをください」と伝えるのがリクエストです。厨房から「カレーができました」と返ってくるのがレスポンスです。

Web アプリでも同じです。

ブラウザがサーバーに「このデータをください」「このデータを保存してください」とお願いします。これが HTTP リクエストです。

サーバーが「このデータです」「保存できました」「エラーです」と返します。これが HTTP レスポンスです。

HTTP には、やりたいことを表す種類があります。代表的なものは GET、POST、PUT、DELETE です。

GET は、データを取るときに使います。

ClearAllergy の例では、メニュー一覧を見るときや、メニュー詳細を見るときに使います。

POST は、新しく作るときに使います。

ClearAllergy の例では、新しいメニューを作るときや、画像をアップロードするときに使います。

PUT は、すでにあるデータを更新するときに使います。

ClearAllergy の例では、メニュー名、価格、説明、アレルゲン状態、公開状態などを保存し直すときに使います。

DELETE は、削除するときに使います。

ClearAllergy の例では、メニューを削除するときに使います。

API とは、画面とサーバーがデータをやり取りする窓口です。

レストランにたとえると、API は「注文を受け付ける窓口」です。お客さんが厨房に直接入って料理を作るのではなく、注文窓口に注文を出します。

Web アプリでも、画面がデータベースを直接触るのではなく、API にお願いをします。

ClearAllergy の例では、次のように考えます。

- メニュー一覧を見る: GET
- 新しいメニューを作る: POST
- メニュー情報を保存する: PUT
- メニューを削除する: DELETE
- 画像をアップロードする: POST

このリポジトリでは、管理画面用の API は主に `app/api/admin` にあります。

公開ページ用の API は `app/api/menus/[menuId]/route.ts` などにあります。

`[menuId]` は「メニュー ID が入る場所」という意味です。たとえば `/api/menus/abc123` の `abc123` が `menuId` になります。

## 5. データベースとは何か

データベース、略して DB は、アプリの記憶場所です。

ClearAllergy では、店舗情報、メニュー情報、アレルゲン情報、ログインユーザーと店舗のつながりなどを保存します。

Excel の表を思い浮かべると近いです。

たとえば、店舗表には「店舗 ID」「店舗名」「住所」「営業時間」などの列があります。メニュー表には「メニュー ID」「店舗 ID」「メニュー名」「価格」「公開状態」などの列があります。

ただし、DB は Excel よりも Web アプリ向きです。多くの人が同時にアクセスしても使いやすく、必要なデータを安全に取り出しやすく、関係のある表同士をつなげやすいからです。

ClearAllergy で画面を閉じてもメニューが消えないのは、DB に保存されているからです。

もし画面の中だけにメニュー名を書いているだけなら、ブラウザを閉じた瞬間に消えてしまいます。DB に保存することで、あとからまた開いても同じデータを取り出せます。

PostgreSQL とは、DB の種類の 1 つです。

車にトヨタ、ホンダ、日産などの種類があるように、DB にも PostgreSQL、MySQL、SQLite などの種類があります。このプロジェクトでは Prisma schema の `datasource db` で `provider = "postgresql"` となっているため、PostgreSQL を使う前提です。

Prisma とは、TypeScript から DB を操作しやすくする道具です。

飲食店のたとえで言うと、DB はお店の台帳です。Prisma は、その台帳に読み書きしてくれる受付係です。

アプリのコードが「この店舗のメニューを取ってきて」と Prisma に頼むと、Prisma が DB に問い合わせます。

アプリのコードが「このメニューを保存して」と Prisma に頼むと、Prisma が DB に書き込みます。

初心者のうちは、Prisma を「DB への読み書きを TypeScript からやりやすくする係」と考えれば十分です。

## 6. TypeScriptとは何か

JavaScript とは、ブラウザやサーバーで動くプログラミング言語です。

画面のボタンを押したときの処理、入力欄の値を読む処理、サーバーでデータを保存する処理などに使われます。

TypeScript は、JavaScript に「型」を追加したものです。

型とは、値の種類を表すルールです。

たとえば、次のような型があります。

- 文字列: `"カレー"`、`"卵"`、`"東京都"` のような文字
- 数値: `800`、`1200`、`0` のような数字
- 真偽値: `true` または `false`

真偽値とは、「はい」か「いいえ」を表す値です。たとえば、公開中なら `true`、非公開なら `false` のように使います。

TypeScript の例です。

```ts
const name: string = "カレー";
const price: number = 800;
const isPublished: boolean = true;
```

1 行目の `const name: string = "カレー";` は、`name` という変数に `"カレー"` という文字列を入れています。`string` は文字列という意味です。

2 行目の `const price: number = 800;` は、`price` という変数に `800` という数値を入れています。`number` は数値という意味です。

3 行目の `const isPublished: boolean = true;` は、`isPublished` という変数に `true` を入れています。`boolean` は真偽値という意味です。`isPublished` は「公開されているかどうか」を表す名前です。

型があると、ミスを減らせます。

たとえば、価格は数値であるべきです。`800` は正しいですが、`"八百円"` のような文字列が入ると、計算や並び替えで困ります。

TypeScript は「ここは数値のはずなのに文字が入っています」と教えてくれます。

ClearAllergy では、型が次のような場面で役立ちます。

- メニュー名は文字列
- 価格は数値または未設定
- 公開状態は真偽値
- アレルゲン状態は決まった選択肢
- 画像 URL は文字列または未設定
- API のレスポンスには決まった形がある

TypeScript の型エラーは、初心者には怖く見えます。しかし型エラーは、アプリが壊れる前に知らせてくれる注意表示です。

レストランで言うと、注文票に「カレー 1 つ」と書くべきところに「カレー たくさん」と書かれていたら、厨房が困ります。TypeScript は、注文票の書き方がおかしいと早めに教えてくれる係です。

## 7. Reactとは何か

React とは、画面を部品として作るための道具です。

部品のことをコンポーネントと呼びます。

コンポーネントとは、画面の一部をまとめたものです。

たとえば、ClearAllergy では次のようなものをコンポーネントとして考えられます。

- メニューカード
- アレルゲン表示
- 保存ボタン
- 画像アップロード欄
- 店舗情報の表示
- 検索ボックス
- ログアウトボタン

飲食店のメニュー表で考えると、「1 つのメニューを表示するカード」を部品として作っておけば、カレーにもパスタにもケーキにも同じ形を使えます。

同じ部品を何度も使えることが React の便利な点です。

たとえば、メニューが 10 件あれば、メニューカードの部品を 10 回使えばよいです。毎回ゼロから画面を作る必要はありません。

React では、状態という考え方も大切です。

状態とは、画面の中で変化する値です。

たとえば、次のようなものが状態です。

- 入力フォームに今入っているメニュー名
- 価格入力欄に入っている数字
- アップロード中かどうか
- 保存中かどうか
- 選択中のアレルゲン状態
- 検索キーワード

状態が変わると、画面も変わります。

たとえば、保存ボタンを押した瞬間に「保存中...」と表示したり、画像を選んだらプレビューを表示したりできます。

初心者のうちは、React を「画面を小さな部品に分けて作るための道具」と考えてください。

## 8. Next.jsとは何か

Next.js とは、React を使って Web アプリを作りやすくするフレームワークです。

フレームワークとは、アプリを作るための土台や決まりごとのことです。

家を建てるとき、柱、床、配線、配管などの基本構造が必要です。フレームワークは、Web アプリを作るための基本構造を用意してくれます。

Next.js では、`app` フォルダの中身が URL と関係します。

`page.tsx` は画面になります。

たとえば、`app/page.tsx` はトップページになります。`app/(public)/shops/page.tsx` は `/shops` の画面になります。

`route.ts` は API になります。

たとえば、`app/api/admin/menus/route.ts` は `/api/admin/menus` の API になります。

Next.js には Server Component と Client Component という考え方があります。

Server Component は、主にサーバー側で動く画面部品です。DB からデータを取って画面を作るような処理に向いています。

Client Component は、主にブラウザ側で動く画面部品です。クリック、入力、画像選択、`useState` のような画面内の状態管理に向いています。

`useState` とは、React で状態を持つための道具です。入力中の文字や、保存中かどうかなど、画面の中で変わる値を扱うときに使います。

ClearAllergy では、公開画面、管理画面、API を Next.js の中でまとめています。

具体的には、公開ページは `app/(public)`、管理画面は `app/admin`、API は `app/api` にあります。

初心者のうちは、Next.js を「URL に対応する画面や API を、決まったフォルダ構成で作れる土台」と考えてください。

## 9. 認証とは何か

認証とは、「あなたは誰ですか」を確認する仕組みです。

ログインとは、本人確認のことです。

飲食店でたとえると、管理画面はお店の事務室です。お客さんは客席には入れますが、事務室には入れません。

お客さんが見る公開ページは、ログイン不要です。なぜなら、お客さんにメニューを見てもらうためのページだからです。

一方、管理画面は飲食店だけが使います。メニューを書き換えたり、価格を変更したり、アレルゲン情報を更新したりできるため、誰でも入れると危険です。

Clerk とは、ログイン機能を安全に作るためのサービスです。

ClearAllergy では、現在の認証は Clerk 前提です。古い NextAuth 前提ではありません。

このリポジトリでは、`app/layout.tsx` に `ClerkProvider` があり、アプリ全体で Clerk の認証情報を使えるようにしています。

また、`proxy.ts` では `clerkMiddleware()` を使って、リクエスト全体で Clerk の認証状態を読めるようにしています。

管理画面では、ログインしている人の情報を使って、その人の店舗データだけを操作します。

ここで大事なのは、画面でボタンを隠すだけでは不十分ということです。

たとえば、他人に見せたくない「削除ボタン」を画面で隠したとしても、悪意のある人が API に直接リクエストを送る可能性があります。

そのため、API 側でもログイン確認が必要です。

ClearAllergy の管理 API では、`requireShopId()` という helper を通して、ログインしているか、店舗を持っているかを確認しています。

さらに、`shopId` をブラウザから送らせて信用するのではなく、サーバー側でログイン情報から店舗 ID を取り直しています。

これはとても重要です。

もし API が body の `shopId` をそのまま信用すると、悪意のある人が別店舗の `shopId` を送って、他店舗のメニューを編集できてしまう可能性があります。

だから、管理 API では「誰がログインしているか」を確認し、その人に紐づく店舗だけを操作する必要があります。

## 10. ClearAllergy全体の流れ

ここでは、ClearAllergy の代表的な 3 つの流れを順番に見ます。

### 10-1. お客さんがメニューを見る流れ

1. お客さんが URL を開く

お客さんがスマホやパソコンのブラウザで店舗ページの URL を開きます。

たとえば `/shops/abc123` のような URL です。`abc123` は店舗 ID のようなものです。

2. 公開ページが表示される

Next.js が URL に対応する画面ファイルを探し、公開ページを表示します。

ClearAllergy では、公開店舗ページは `app/(public)/shops/[shopId]/page.tsx` にあります。

3. サーバーが DB からメニュー情報を取る

画面を作るために、サーバーが DB から店舗情報や公開中メニューを取得します。

公開ページなので、非公開メニューは表示しません。

4. アレルゲン情報が画面に表示される

DB から取ったメニュー情報とアレルゲン情報を使って、お客さんの画面に表示します。

お客さんは、メニューごとにアレルゲン状態を確認できます。

### 10-2. 店舗管理者がメニューを作る流れ

1. 店舗管理者がログインする

飲食店の管理者は、Clerk のログイン機能を使って本人確認をします。

2. 管理画面を開く

ログイン済みで、店舗が紐づいている管理者だけが管理画面へ進めます。

管理画面の共通 layout では、`requireCurrentAdminContextOrRedirect()` によって、未ログインならログイン画面、店舗未作成なら登録画面へ送る処理があります。

3. メニュー名や価格を入力する

管理者は、メニュー作成画面でメニュー名、説明、価格、カテゴリ、材料、注意事項、アレルゲン状態などを入力します。

4. 保存ボタンを押す

保存ボタンを押すと、ブラウザから API にデータが送られます。

5. API にデータが送られる

新規作成では、`app/api/admin/menus/route.ts` の `POST` が使われます。

既存メニューの更新では、`app/api/admin/menus/[menuId]/route.ts` の `PUT` が使われます。

6. DB に保存される

API は、ログイン確認と店舗確認をしたうえで、Prisma を使って DB に保存します。

メニュー本体は `MenuItem` に保存されます。

メニューごとのアレルゲン状態は `MenuItemAllergen` に保存されます。

7. 公開ページに反映される

メニューが公開状態になっていれば、お客さんが見る公開ページにも表示されます。

非公開状態なら、管理画面には見えても、お客さんの公開ページには表示されません。

### 10-3. 店舗管理者が画像をアップロードする流れ

1. 画像を選ぶ

管理者がメニュー画像や店舗画像を選びます。

2. API に画像を送る

ブラウザは画像ファイルを API に送ります。

メニュー画像の場合は `app/api/admin/upload-menu-image/route.ts` が使われます。

店舗画像の場合は `app/api/admin/upload-shop-image/route.ts` が使われます。

3. Vercel Blob に保存する

Vercel Blob とは、画像などのファイルを保存するためのサービスです。

DB は表形式のデータ保存に向いていますが、画像ファイルそのものを大量に入れる場所としては扱いづらいことがあります。

そのため、画像ファイルは Vercel Blob に保存し、DB には画像の URL を保存します。

4. 画像 URL を DB に保存する

画像を Vercel Blob に保存すると、画像を表示するための URL が得られます。

その URL をメニューや店舗のデータに保存します。

5. 画面で画像を表示する

公開ページや管理画面は、DB に保存された画像 URL を使って画像を表示します。

## 11. appフォルダの読み方

Next.js App Router では、`app` フォルダの中の構成が URL と関係します。

App Router とは、Next.js のルーティング方式です。ルーティングとは、URL と画面や API を対応させる仕組みです。

`page.tsx` は画面です。

`layout.tsx` は共通の外枠です。

`route.ts` は API です。

ClearAllergy の主な `app` フォルダは次のように読めます。

`app/(public)` は、公開ページのまとまりです。

`(public)` のような括弧付きフォルダは、URL には出ません。整理用のフォルダです。

たとえば、`app/(public)/shops/page.tsx` は `/shops` になります。URL に `(public)` は入りません。

`app/admin/(auth)` は、管理者のログインや登録に関係する画面のまとまりです。

`(auth)` も括弧付きなので URL には出ません。

`app/admin/(dashboard)` は、ログイン後の管理画面のまとまりです。

`app/api` は API のまとまりです。

`app/api/admin/menus/route.ts` は `/api/admin/menus` という API になります。

`[menuId]` のような角括弧付きフォルダは、動的 URL です。

動的 URL とは、URL の一部が毎回変わるものです。

たとえば、メニュー ID が `abc123` のときは `/admin/menus/abc123/edit`、メニュー ID が `xyz789` のときは `/admin/menus/xyz789/edit` になります。

どちらも同じ画面ファイルで扱いたいので、フォルダ名を `[menuId]` にします。

具体例です。

`app/admin/(dashboard)/menus/[menuId]/edit/page.tsx`

これは、次のような URL に対応します。

`/admin/menus/abc123/edit`

理由は次の通りです。

- `app` は URL の土台なので URL には出ない
- `admin` は URL に出る
- `(dashboard)` は括弧付きなので URL に出ない
- `menus` は URL に出る
- `[menuId]` は実際のメニュー ID に置き換わる
- `edit` は URL に出る
- `page.tsx` は画面ファイルなので URL には出ない

その結果、`/admin/menus/abc123/edit` のような URL になります。

## 12. Prisma schema の読み方

Prisma schema は、DB の設計図です。

このプロジェクトでは `prisma/schema.prisma` にあります。

`model` とは、DB の表の設計図です。

たとえば `model Shop` は、店舗テーブルの設計図です。

`field` とは、表の列です。

たとえば `Shop` の `name` は店舗名、`address` は住所、`isActive` は有効な店舗かどうかを表す列です。

`relation` とは、表同士のつながりです。

たとえば、1 つの店舗には複数のメニューがあります。これは `Shop` と `MenuItem` のつながりです。

`enum` とは、決まった選択肢です。

たとえば `AllergenStatus` には、次の選択肢があります。

- `CONTAINS`: 含む
- `FREE`: 含まない
- `MAY_CONTAIN`: 含む可能性がある
- `UNKNOWN`: 未確認、または不明

ClearAllergy の主な model は次の通りです。

`User` は、アプリ内のユーザーを表します。

現在の認証は Clerk を正として扱い、`clerkUserId` で Clerk ユーザーとアプリ内 User を結びつけます。

`Shop` は、飲食店を表します。

店舗名、説明、住所、営業時間、電話番号、画像 URL、公開に使う情報などを持ちます。

`MenuItem` は、メニューを表します。

メニュー名、説明、価格、カテゴリ、材料、注意事項、画像 URL、公開状態などを持ちます。

`Allergen` は、アレルゲンのマスタ情報を表します。

マスタ情報とは、アプリ全体で共通して使う基本データのことです。卵、乳、小麦などの一覧がここに入ります。

`MenuItemAllergen` は、メニューとアレルゲンのつながりを表します。

たとえば「カレーは卵を含まない」「カレーは小麦を含む可能性がある」のような情報です。

1 対 1、1 対 多、多 対 多も、飲食店の例で考えると理解しやすくなります。

1 対 1 は、1 つのものに 1 つのものが対応する関係です。

ClearAllergy では、1 人の User が 1 つの Shop を持つような関係に近いです。schema では `Shop.userId` に `@unique` があり、1 つの User に対して 1 つの Shop という制約を表しています。ただし現在は Clerk 移行後の互換もあるため、所有者判定では `ownerClerkUserId` が重要です。

1 対 多は、1 つのものが複数のものを持つ関係です。

1 つの Shop は複数の MenuItem を持てます。つまり、1 つの飲食店に、カレー、パスタ、サラダ、ケーキなど複数のメニューがあります。

多 対 多は、複数同士がつながる関係です。

1 つの MenuItem は複数の Allergen と関係します。カレーは卵、小麦、乳など複数のアレルゲン状態を持つ可能性があります。

同時に、1 つの Allergen も複数の MenuItem と関係します。卵というアレルゲンは、カレー、オムライス、ケーキなど複数のメニューに関係する可能性があります。

このように、MenuItem と Allergen は多 対 多の関係です。

DB では、多 対 多をそのまま保存するのではなく、中間テーブルを使うことがよくあります。

ClearAllergy では、その中間テーブルが `MenuItemAllergen` です。

特に大事なのは、1 つの MenuItem は 28 品目それぞれの Allergen 状態を持つという考え方です。

この「28 品目」はコードコメントや画面説明に出てきます。実際に seed やマスタデータで何件登録されるかは `prisma/seed.ts` も合わせて要確認です。

`MenuItemAllergen` には、`menuItemId`、`allergenId`、`status` があります。

`menuItemId` は、どのメニューかを表します。

`allergenId` は、どのアレルゲンかを表します。

`status` は、そのメニューがそのアレルゲンをどう扱うかを表します。

たとえば、カレーと卵の組み合わせに対して `FREE` が入っていれば、「このカレーは卵を含まない」と表せます。

カレーと小麦の組み合わせに対して `MAY_CONTAIN` が入っていれば、「このカレーは小麦を含む可能性がある」と表せます。

`UNKNOWN` と `FREE` は違います。

`FREE` は「含まないと確認済み」です。

`UNKNOWN` は「まだ不明」「未確認」です。

アレルギー情報では、この違いがとても重要です。

わからないものを「含まない」と扱うと危険です。だから、未確認の場合は `UNKNOWN` として安全側に倒します。

## 14. つまずきポイント集

### URLとフォルダの対応がわからない

原因:
Next.js では `app` フォルダの構成が URL になるため、普通のフォルダ整理とは少し感覚が違います。

どこを見る:
`app` フォルダ全体、特に `page.tsx`、`route.ts`、括弧付きフォルダ、角括弧付きフォルダを見ます。

どう考える:
`page.tsx` は画面、`route.ts` は API です。`(public)` のような括弧付きフォルダは URL に出ません。`[shopId]` や `[menuId]` は URL の変わる部分です。

### page.tsxとroute.tsの違いがわからない

原因:
どちらも TypeScript のファイルなので、最初は同じに見えます。

どこを見る:
`app/(public)/shops/[shopId]/page.tsx` と `app/api/menus/[menuId]/route.ts` を比べます。

どう考える:
`page.tsx` は人間が見る画面を返します。`route.ts` は画面ではなく、データを JSON などで返す API です。

### APIとDBの違いがわからない

原因:
どちらも「裏側」の話なので混ざりやすいです。

どこを見る:
`app/api/admin/menus/route.ts` と `prisma/schema.prisma` を見ます。

どう考える:
API は注文窓口です。DB は台帳です。画面は API にお願いし、API が DB を読み書きします。

### TypeScriptの型エラーが怖い

原因:
赤いエラーが出ると、壊したように見えるからです。

どこを見る:
エラーが出ている行と、その変数がどんな値を期待しているかを見ます。

どう考える:
型エラーは、実行前にミスを教えてくれる注意表示です。価格に文字列が入っている、存在しない項目を読もうとしている、未設定の可能性がある値をそのまま使っている、などを知らせてくれます。

### Server ComponentとClient Componentがわからない

原因:
どちらも React のコンポーネントですが、動く場所が違います。

どこを見る:
DB を直接読んでいる `page.tsx` と、`"use client"` が付いたコンポーネントを比べます。

どう考える:
Server Component はサーバー側でデータ取得や画面作成をします。Client Component はブラウザ側でクリック、入力、状態変化を扱います。

### useStateが使える場所と使えない場所がわからない

原因:
`useState` はブラウザ側で動く React の機能なので、すべてのファイルで使えるわけではありません。

どこを見る:
`components/admin/menu/NewMenuForm.tsx` や `components/admin/menu/MenuEditClient.tsx` のような Client Component を見ます。

どう考える:
`useState` を使うファイルには基本的に `"use client"` が必要です。DB からデータを取る Server Component ではなく、入力欄やボタンの状態を持つ Client Component で使います。

### 401 / 403 / 404 / 500 がわからない

原因:
HTTP ステータスコードは数字だけなので、最初は意味がわかりにくいです。

どこを見る:
`app/api/admin/_utils.ts` や各 API の `NextResponse.json(..., { status: ... })` を見ます。

どう考える:
`401` は未ログインです。`403` はログインしているが権限や準備が足りない状態です。`404` は見つからない状態です。`500` はサーバー側の予期しないエラーです。

### DBのリレーションがわからない

原因:
表が複数に分かれていて、どこに何が保存されるかわかりにくいからです。

どこを見る:
`prisma/schema.prisma` の `Shop`、`MenuItem`、`Allergen`、`MenuItemAllergen` を見ます。

どう考える:
店舗とメニューは、1 つの店舗が複数のメニューを持つ関係です。メニューとアレルゲンは、多くのメニューと多くのアレルゲンが関係するため、中間テーブルを使います。

### 中間テーブルがわからない

原因:
メニュー表とアレルゲン表だけでよさそうに見えるからです。

どこを見る:
`MenuItemAllergen` を見ます。

どう考える:
カレーと卵、カレーと小麦、パスタと卵、パスタと小麦のように、「メニューとアレルゲンの組み合わせごとの状態」を保存する必要があります。その組み合わせを保存する場所が中間テーブルです。

### UNKNOWNとFREEの違いがわからない

原因:
どちらも「含むとは言っていない」ように見えるからです。

どこを見る:
`AllergenStatus` enum と、アレルゲン状態を表示しているコンポーネントを見ます。

どう考える:
`FREE` は「含まないと確認済み」です。`UNKNOWN` は「未確認」です。アレルギー情報では、未確認を含まない扱いにしてはいけません。

### 認証しているのに、さらに所有確認が必要な理由がわからない

原因:
ログインできたら何でも操作できるように感じるからです。

どこを見る:
`lib/admin-auth.ts`、`app/api/admin/_utils.ts`、`app/api/admin/menus/[menuId]/route.ts` を見ます。

どう考える:
ログインは「あなたは誰ですか」の確認です。所有確認は「このデータはあなたの店舗のものですか」の確認です。ログイン済みでも、他店舗のメニューを編集できてはいけません。

## 15. 今は深追いしなくてよいこと

Next.js の高度なキャッシュ:
キャッシュとは、一度取ったデータを再利用して速くする仕組みです。重要ですが、最初は「画面、API、DB の流れ」を優先した方が理解しやすいです。

ISR:
ISR は、ページを一定間隔で再生成するような Next.js の高度な機能です。ClearAllergy の基本理解では、まず通常のページ表示と API を理解すれば十分です。

Edge Runtime:
Edge Runtime は、サーバー処理を利用者に近い場所で動かすための仕組みです。最初から理解しようとすると、サーバーの場所や実行環境の話に寄りすぎます。

Prisma の高度な最適化:
DB 問い合わせを速くする工夫は大切ですが、最初は `findMany`、`findFirst`、`create`、`update`、`delete` の意味を理解する方が先です。

PostgreSQL の内部構造:
PostgreSQL が内部でデータをどう保存しているかは、最初は不要です。まずは「表形式でデータを保存する場所」として理解してください。

Clerk の内部実装:
Clerk が内部でログインセッションをどう管理しているかは高度です。最初は「ログイン機能を安全に提供するサービス」と考えれば十分です。

Vercel Blob の細かい課金仕様:
料金や細かい制限は運用時に重要ですが、最初の学習では「画像などのファイルを保存する場所」と理解すれば十分です。実運用前には公式情報で要確認です。

React の高度なレンダリング最適化:
再レンダリングの細かい最適化は、React に慣れてからで大丈夫です。最初はコンポーネント、props、状態、イベントを理解しましょう。

セキュリティの全分野:
CSRF、XSS、CORS、レート制限などは重要ですが、一気に全部覚える必要はありません。ClearAllergy では、まず「API 側でもログイン確認する」「body の shopId を信用しない」を理解してください。

## 17. まとめ

最初から全部理解しなくて大丈夫です。

Web アプリは、最初に見る範囲が広く感じます。画面、API、DB、ログイン、型、フォルダ構成が一度に出てくるからです。

まずは「画面 → API → DB」の流れを追ってください。

お客さんが画面を開く。画面が必要なデータを表示する。管理者が保存ボタンを押す。API が受け取る。DB に保存される。この流れを 1 つずつ見れば、全体像がつかみやすくなります。

次に、「ログインしている人だけが管理できる」仕組みを見ます。

ログインしているかどうかだけでなく、その人がどの店舗を操作できるかを確認することが大切です。画面でボタンを隠すだけでは足りません。API 側でも必ず確認します。

1 つの機能を最後まで追えるようになることが重要です。

たとえば「メニューを作る」という機能なら、メニュー作成画面、保存ボタン、管理 API、Prisma、DB の `MenuItem` と `MenuItemAllergen` までを順番に追います。

ClearAllergy は、実際の Web アプリの基本要素がまとまっています。

公開ページ、管理画面、API、DB、認証、画像アップロード、TypeScript、React、Next.js、Prisma、PostgreSQL、Clerk、Vercel Blob が 1 つのプロジェクトに入っています。

そのため、Web アプリ開発の基礎を学ぶ教材として使いやすいプロジェクトです。

迷ったら、難しい言葉から入るのではなく、次の質問に戻ってください。

- 押したあと、どの API に送られるか
- API はログインや所有確認をしているか
- DB のどの表に保存されるか
- 保存されたデータは、どの画面に表示されるか

この順番で読めるようになると、ClearAllergy だけでなく、他の Web アプリのコードも少しずつ読めるようになります。
