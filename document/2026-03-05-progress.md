## 1. 管理側API（admin）を整備

### 実装した/確認したAPI

- POST `/api/admin/menus`
    - 新規メニュー作成（name必須、shopIdはsessionから）
    - 成功時は `{ id }` を返す（作成後に編集ページへ遷移するため）
- GET `/api/admin/menus/:menuId`
    - 管理用詳細取得（shopId一致のみ）
- PUT `/api/admin/menus/:menuId`
    - 更新（shopIdはbodyで受けずsessionから）
    - アレルゲン更新は `allergenStatusBySlug` を受けて upsert
    - 「存在しないslugは400で返す」チェックを追加
    - upsertは transaction でまとめて中途半端更新を防止
- GET `/api/admin/menus`
    - 一覧取得（updatedAt desc）
- DELETE `/api/admin/menus/:menuId`
    - 削除（shopId一致のみ）
    - 中間テーブル（menuItemAllergen）を先に deleteMany → 本体 delete

### 学び

- shopIdをbodyで受けるのは危険（他店のデータを書き換えられる）  
  → session.user.shopId を唯一の根拠にする
- アレルゲン更新は「一部だけ成功」が起きやすい  
  → `$transaction` でまとめるのが安全
- slug間違いは「反映されない」になりがち  
  → missing slug を 400 で返すとデバッグが速い

## 4. 重要な落とし穴：paramsがundefinedでPrismaが落ちる

### 症状

- `findUnique where: { id: undefined }`
- PrismaClientValidationError: `ShopWhereUniqueInput needs at least one of id or userId`

### 原因

- Next.js 16 + Turbopack環境で `params` が Promise の形になることがあり、
  `params.shopId` を直接読むと undefined になるケースがある

### 対処（正解パターン）

- `params: Params | Promise<Params>` として受ける
- 必ず `const { shopId } = await params;` を最初に書く
- `where: { id: shopId }` を使う（params.shopIdは使わない）
- 旧コードが残ると再発するので「ファイルを丸ごと置換」が安全
