# 2026-04-06 作業まとめ

## 1. 今日の目的
今日は、ClearAllergy を本番公開に近づけるために、特に危険度の高かった部分を順番に直しました。主な目的は、アレルゲン情報の誤表示を防ぐこと、古い危険な API を止めること、認証や登録や画像アップロードの入口を固くすること、そして後から何をしたのか追えるようにすることでした。

この修正が必要だった理由は、このサービスが「店舗のメニューに含まれるアレルゲン情報を利用者が確認する」ものだからです。普通の文言ミスよりも、「未確認なのに安全に見える」「不完全な情報が公開される」「古い API から抜け道が残る」といった問題の方がずっと危険です。今回は、そうした本番前に止めるべき点を先に潰すことを目標にしました。

## 2. 背景にあった問題
レビューで最初に見つかった大きな問題は、未設定のアレルゲンが `FREE` と同じように扱われていたことです。`FREE` は「含まないと確認した」という意味ですが、未設定は「まだ確認できていない」という全く別の状態です。この 2 つを同じにしてしまうと、利用者からは「安全」と誤解される可能性があります。

次に問題だったのは、公開条件が UI に偏っていて、API を直接叩けば不完全なメニューを公開できる余地があったことです。メニュー名だけあって、原材料名や注意書きや 28 品目の確定が無くても `isPublished: true` にできる状態は、本番では危険です。

さらに、古い API が残っていて、現在の認可や公開条件を通らずにデータを作れてしまう経路もありました。認証まわりではレート制限が無かったため、ログイン総当たりや BOT 登録に弱く、画像アップロードもサイズや種別のチェックが不足していました。こうした理由から、当初の状態ではそのまま本番公開できませんでした。

## 3. 今日変更した主な内容
まず、`UNKNOWN` という状態を正式に導入しました。これは「まだ未設定・未確認」という意味です。ここで大事なのは、`FREE` と混ぜないことです。`FREE` は店舗が「含まない」と判断した状態ですが、`UNKNOWN` はまだ判断できていない状態です。この違いをはっきり分けることで、利用者に誤った安心感を与えないようにしました。

次に、古い公開 API を停止しました。レビューで見つかった `_disabled` ルートは、名前からすると止めてあるように見えますが、実際には残っているだけで危険です。古い API が 1 本でも生きていると、現在の認可やバリデーションを迂回される可能性があります。そのため、「使っていないから大丈夫」ではなく、実際に route を削除して 404 にしました。

既存公開データの是正スクリプトも追加しました。コードだけ直しても、すでに DB に危険なデータが入っていれば意味がありません。今回のスクリプトでは、28 品目の欠損行を `UNKNOWN` で補完し、公開条件を満たしていないメニューは自動で下書きに戻すようにしました。これは migration ではなく one-shot script にしたので、本番反映時に一度だけ意図を持って実行できます。

`seed` も安全側に直しました。開発用データだからといって不完全な公開データを作ってしまうと、後から画面を見た人が「この挙動で正しいのだろう」と誤解します。そこで、公開デモメニューには 28 品目を必ず全部作るようにし、平文パスワードをログへ出す処理も削除しました。`seed` は単なるおまけではなく、将来の理解や検証の土台になるので、ここも大切です。

GET API も 28 品目で正規化するようにしました。以前は、DB 上にリンクがあるアレルゲンだけ返す形だったため、API 利用側が「項目が無いのは安全なのか、未設定なのか」を解釈できませんでした。今は、公開 API でも管理 API でも 28 品目を必ず返し、欠損は `UNKNOWN` として見えるようにしています。これで、画面表示と API の意味がずれにくくなりました。

公開 UI の文言も統一しました。メニュー一覧の要約や、詳細画面の警告バナーや、特定原材料の notice で `UNKNOWN` が途中で落ちてしまうと、「危険なものだけ見えて、未設定が見えない」という分かりにくい表示になります。今回は、`含む` や `可能性あり` がある時でも `未設定` が残るようにし、利用者が「まだ未確認の項目がある」ことを見落としにくくしました。

認証と登録にはレート制限を追加しました。レート制限とは、短時間に大量のリクエストが来た時に止める仕組みです。ログイン API と登録 API に IP 単位の最小構成の制限を入れ、少なくとも総当たりや BOT の連打に対して無防備ではない状態にしました。今回は in-memory の簡易版ですが、「何も無い」よりは明確に前進です。

`/admin/register` はモード制御できるようにしました。常に開放された登録画面があると、誰でも店舗アカウントを作れてしまいます。そこで、`disabled`、`invite_only`、`open` の 3 モードを用意し、画面側だけでなく API 側でも同じガードをかけました。特に `open` は危険で、本番では BOT 登録やなりすましの入口になり得るため、使う場合は本人確認や審査が別途必要です。

画像アップロード検証も強化しました。画像は見た目の機能ですが、実は危険な入口にもなります。サイズが大きすぎるとコストや障害の原因になりますし、形式を制限しないと予期しないファイルを混ぜられる可能性があります。今回は MIME の許可リスト、5MB 上限、失敗時の JSON 応答を共通化し、エラー時にもクライアントが扱いやすいようにしました。

最後に、seed の平文パスワードログを削除しました。DB 保存は最初からハッシュ化されていましたが、ログに平文を出してしまうと、CI やサーバーログに認証情報が残る危険があります。初心者のうちは「開発用だから」と見過ごしやすい部分ですが、運用ではとても重要です。

## 4. 変更したファイル一覧と役割
`lib/allergens.ts` は、アレルゲン状態の共通ロジックをまとめたファイルです。`UNKNOWN` を正式に扱い、28 品目をそろえる処理、公開条件の判定、特定原材料の notice をここに集約しました。ここを直した理由は、画面ごとに判定がずれると事故が起きやすいからです。

`app/api/admin/menus/route.ts` と `app/api/admin/menus/[menuId]/route.ts` は、管理画面のメニュー作成・更新 API です。公開時のサーバー側バリデーションをここに入れました。理由は、UI だけで必須チェックしても API 直打ちで抜けられるからです。

`app/api/menus/[menuId]/route.ts` は、公開側のメニュー詳細 API です。28 品目を `UNKNOWN` 含みで正規化して返すようにしました。理由は、DB の欠損をそのまま API 契約に出すと、利用者側が意味を誤解しやすいからです。

`components/public/ShopMenuListClient.tsx` と `components/public/MenuAllergenAlertClient.tsx` は、公開 UI の表示ロジックです。要約文、件数表示、警告バナーで `UNKNOWN` が落ちないように直しました。理由は、「危険があるものだけ見えて、未設定は消える」という状態が利用者にとって分かりにくかったからです。

`app/(public)/shops/[shopId]/page.tsx` は、公開店舗ページです。公開メニューが 1 件も無い店舗は 404 にする条件を入れました。理由は、公開前の店舗情報だけが見えてしまう状態を防ぐためです。

`prisma/repair-published-menus.ts` は、既存公開データを是正する one-shot script です。欠損アレルゲンを `UNKNOWN` で埋め、不完全な公開メニューを下書きへ戻します。コードを直すだけでは既存 DB の問題は消えないため、このスクリプトが必要でした。

`prisma/seed.ts` は、開発用データの作成スクリプトです。公開デモメニューを 28 品目完全化し、パスワードログを削除しました。seed も理解用資料の一部なので、安全な状態にしておく必要があります。

`lib/request-ip.ts` と `lib/rate-limit.ts` は、レート制限の土台です。送信元 IP を取り出し、簡易レート制限を行います。理由は、ログインや登録を短時間に何度も叩ける状態が危険だったからです。

`lib/admin-registration.ts`、`app/api/admin/register/route.ts`、`app/api/admin/onboarding/route.ts`、`app/admin/(auth)/register/page.tsx`、`components/admin/auth/AdminRegisterPageClient.tsx`、`components/admin/auth/AdminOnboardingPageClient.tsx` は、登録モード制御に関係するファイルです。登録を `disabled` / `invite_only` / `open` で切り替えられるようにしました。理由は、登録画面の開放がそのまま攻撃面になるからです。

`lib/upload-images.ts`、`app/api/admin/upload-shop-image/route.ts`、`app/api/admin/upload-menu-image/route.ts` は、画像アップロードの共通処理と API です。サイズ上限、許可 MIME、JSON エラー応答をまとめました。理由は、画像アップロードがストレージ濫用や不正ファイル送信の入口になるからです。

`lib/audit-log.ts`、`prisma/schema.prisma`、`prisma/migrations/20260405010000_add_audit_log/migration.sql` は、監査ログ対応です。誰が・何を・いつ・成功/失敗したかを追えるようにしました。理由は、本番運用では「何が起きたか分からない」状態が一番危ないからです。

`lib/image-url-policy.ts`、`app/api/admin/shop/route.ts`、`app/api/admin/menus/route.ts`、`app/api/admin/menus/[menuId]/route.ts`、`app/api/menus/[menuId]/route.ts` は、画像 URL 保存ルールの厳格化に関係します。自前アップロード由来の URL だけ保存・表示するようにしました。理由は、外部 URL を自由入力できると、追跡用画像や他店舗画像の使い回しが起きるからです。

`lib/auth.ts` は、旧メールアドレス+パスワード認証の本体です。`bcrypt.compare` による照合と、ログイン試行のレート制限を追加しました。理由は、パスワードがハッシュ化されていても、総当たり対策が無いと危険だからです。

## 5. 特に重要な考え方
`UNKNOWN` と `FREE` は似て見えますが、意味は全く違います。`FREE` は「店舗が含まないと確認した」という状態です。一方で `UNKNOWN` は「まだ確認できていない」状態です。利用者にとっては、この差はとても重要です。未確認なのに `FREE` 扱いしてしまうと、「安全だ」と誤解されるからです。

公開条件をサーバー側でチェックする理由は、フロントエンドだけでは守り切れないからです。フロントエンドは画面の都合で崩れることもありますし、API はブラウザ以外からも叩けます。だからこそ、「公開してよいか」は最後にサーバー側が判断する必要があります。

古い API を消す必要があるのは、今の安全なルールを守っていない可能性が高いからです。コードベースの中に「昔のまま」の入口が残っていると、そこから抜けられてしまいます。使っていないつもりでも、URL が存在するだけで攻撃面になるので、残すより消す方が安全です。

seed も安全にしておく必要があります。初心者のうちは、seed を「とりあえず表示確認用」と考えがちですが、実際には開発中に何度も参照する重要なデータです。seed が不完全だと、その不完全さを「仕様」だと勘違いしてしまいます。だから seed も本番に近い安全な形にしておくべきです。

レート制限が必要なのは、正しい認証実装だけでは防げない攻撃があるからです。たとえば、パスワードをハッシュ化していても、短時間に大量ログインを試されると危険です。レート制限は「短時間の連続試行を止める壁」です。

アップロード検証が必要なのは、画像が単なる見た目の機能ではないからです。大きすぎるファイルはサーバーコストや障害の原因になりますし、許可していない形式は想定外の処理を引き起こすことがあります。アップロードは外からファイルを受け取る処理なので、特に慎重に扱う必要があります。

## 6. 確認手順
1. 依存関係と Prisma の生成物を最新化します。

```bash
npx prisma migrate deploy
npx prisma generate
```

2. 既存公開データの是正スクリプトを 1 回実行します。

```bash
npm run repair:published-menus
```

3. 開発用データを入れ直したい場合だけ seed を実行します。

```bash
npm run seed
```

4. ビルドが通るか確認します。

```bash
npm run build
```

5. 管理画面でメニューを新規作成し、28 品目の一部を未設定のまま公開しようとして 400 になることを確認します。

6. 28 品目をすべて設定し、原材料名と注意書きを入れた場合にだけ公開できることを確認します。

7. 公開メニュー詳細画面で、未設定項目が `未設定` として見え、`含まない` になっていないことを確認します。

8. 店舗一覧と店舗詳細のメニューカードで、件数表示と要約文の両方に `未設定` の情報が残ることを確認します。

9. `/admin/register` のモードを切り替えて、`disabled` では閉じる、`invite_only` では招待トークンが必要、`open` では開くことを確認します。

10. ログイン API と登録 API を短時間に連続実行し、429 もしくは制限が効くことを確認します。

11. 画像アップロードで 5MB 超や許可外 MIME を送って、JSON エラーが返ることを確認します。

12. 監査ログテーブルに、メニュー作成・公開切替・店舗更新・画像アップロードの成功/失敗が残ることを確認します。

## 7. まだ残っている課題
監査ログは今回追加しましたが、まだ「記録できるようになった」段階です。次は、管理画面から見られるのか、アラートと連携するのか、失敗が多い時にどう気付くのか、といった運用面を整える必要があります。

画像URL保存ルールも今回かなり厳格化しましたが、既存 DB に残っている外部 URL を完全に掃除する運用や、許可 prefix の本番設定確認はまだ必要です。表示時の防御は入っていますが、データクレンジングまで済ませるとより安全です。

公開登録を `open` で使う場合の本人確認は、まだ残課題です。`open` モードは開発や限定運用では便利ですが、本番で広く使うにはメール確認や審査フローが欲しいです。今のまま `open` を使うのは危険です。

店舗ページ公開条件も、今回「公開メニューが 1 件以上あること」を条件にしましたが、今後は「店舗自体の公開/非公開」フラグを持たせるかどうかを検討してもよいです。店舗情報だけを段階的に準備したい場合は、より明示的な設計が必要になります。

レート制限は現在 in-memory のため、アプリを複数台に増やした時に共有されません。将来的に本番規模を大きくするなら、Redis などの共有ストアへ移す必要があります。

## 8. 今日学んだこと
未設定と安全は同じではない、という点がとても重要だと分かりました。データが無いことを「問題なし」と見せてしまうと、画面上は親切に見えても実際には危険です。

また、フロントエンドの見た目を直すだけでは安全にならず、サーバー側のバリデーションや古い API の整理が必要だと分かりました。本番前の修正は、見た目よりも「抜け道を減らす」ことが大切です。

さらに、seed やログや画像 URL のような一見小さく見える部分も、運用では大きな事故につながることがあると学びました。

## 9. 次にやること
1. 共有ストア型のレート制限へ移行する  
理由: 複数インスタンス構成でも確実に効かせるためです。

2. 監査ログの閲覧・通知運用を整える  
理由: 記録するだけでは気付けないので、運用で使える形にする必要があります。

3. 外部画像 URL の既存データを洗い出して整理する  
理由: 表示時の防御だけでなく、DB の中身自体も安全にしたいからです。

4. 登録 open モードを使うなら本人確認フローを追加する  
理由: 公開登録を安全に残すには、なりすまし対策が必要です。

5. 店舗公開の設計を明示化する  
理由: 今は公開メニュー件数で間接的に制御しているため、将来は店舗単位の公開状態を持つ方が分かりやすい可能性があります。
