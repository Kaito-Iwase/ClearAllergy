## 1. 今日やったこと（作業ログ：時系列）

### 1) NextAuth（Credentials）導入の準備
- `npm i`（依存追加）を実行し、`package.json` / `package-lock.json` をコミットして区切りを作った

**学び**
- 大きい機能（認証）を入れる前に「動く状態」をcommitしておくと安全。

---

### 2) PrismaスキーマがCredentialsに適合していることを確認
確認したモデル：
- `User(email @unique, passwordHash)`
- `Shop(userId @unique)`（User 1 : 1 Shop）

**学び**
- Credentials認証は **email** と **passwordHash（bcrypt）** が揃っていると実装が簡単。
- 平文パスワードはDBに保存しない（ハッシュ化して保存）。

---

### 3) bcrypt の型問題と `any` 問題を解消
- `bcrypt` の型定義不足 → `@types/bcrypt` を追加（またはbcryptjsへ切替）
- NextAuthの `as any` による警告（Unexpected any） → `types/next-auth.d.ts` に型拡張を追加して `any` を排除

作った/直したもの（要点）：
- `types/next-auth.d.ts`  
  - `Session.user.userId / shopId`
  - `JWT.userId / shopId`
  - `User.shopId`
- `tsconfig.json` の `include` に `types/**/*.d.ts` を追加（JSONの構文ミスも修正）

**学び**
- `"use client"` と同じで「型拡張（d.ts）」も **読み込ませる設定**が必須。
- `any` を消すと、後の改修（セッション参照など）が安全になる。

---

### 4) NextAuth設定を「A方式」に整理（authOptionsを切り出し）
- 元：`app/api/auth/[...nextauth]/route.ts` に全部ベタ書き（B方式）
- 変更：`lib/auth.ts` に `authOptions` を切り出し（A方式）
  - `authorize`：email→User取得→bcrypt比較→Shop取得→ `shopId` を返す
  - `callbacks.jwt`：tokenへ `userId/shopId`
  - `callbacks.session`：sessionへ `userId/shopId`

**学び**
- `authOptions` を切り出すと、API・ページ・middlewareで **使い回し**ができる。

---

### 5) 管理APIをセッションshopIdに寄せる（クライアントからshopIdを送らない）
- `PUT /api/admin/menus/:menuId` を **body.shopId依存から脱却**
  - `getServerSession(authOptions)` でshopId取得
  - `where: { id: menuId, shopId }` で権限チェック
- 管理編集UI（Client）側は `body` から `shopId` を削除

**学び**
- `shopId` をクライアントが送る方式は改ざん余地が残る
- **サーバがセッションからshopIdを決める**のが安全。

---

### 6) テストユーザー作成でts-node/esmが詰まった → tsx採用
- Node 22 + `--loader ts-node/esm` で `ERR_REQUIRE_CYCLE_MODULE` が出た
- 対処：`tsx` を導入して `npx tsx ...` で実行（TypeScript実行が安定）

**学び**
- NodeのESM/CJS周りは環境差で詰まりやすい。開発中は `tsx` が速い。

---

### 7) ログインページのURLがズレて 404 → フォルダ構造を統一
発生：
- `/admin/login` に飛ぶのに、実体が `app/(admin)/admin/auth/login/page.tsx`（= `/admin/auth/login`）で404

対応：
- `auth` を整理して **ログインURLを `/admin/login` に統一**（またはURL側を合わせる）
- `redirect("/admin/...")` の遷移先も統一
- `middleware.ts` の matcher 除外も統一（ログインページが弾かれないようにする）

**学び**
- Next.jsは「フォルダ＝URL」なので、**置き場所とURLがズレると即404**。
- ルーティング整理後は `.next` 削除→再起動が安全。

---

### 8) セッションshopIdとメニューのshopId不一致で「一覧が空」→ 原因特定して修正
現象：
- `shopId(session): cmm90... / 件数: 0` と表示（デバッグ表示で確認）

原因：
- 既存メニューの `MenuItem.shopId` と、ログイン中セッションの `shopId` が違う

対応：
- `MenuItem.shopId` を「ログイン中shopId」に揃え、一覧表示＆編集が正常化
- デバッグ表示（`shopId(session) ...`）は原因特定後に削除

**学び**
- 認証導入後は「どのshopに紐づくデータか」が重要。
- 0件のときは **セッションshopId** を画面に出すと一発で原因が分かる。

## 2. 学習メモ（小さいことから）

### 2.1 `redirect("/admin/login")` は何？
- Server Componentで「未ログインならログインページへ飛ばす」処理
- ログインURLを変えたら `redirect` も必ず合わせる

### 2.2 middlewareの matcher の役割
- `/admin/*` を保護するが、`/admin/login` は除外しないとログインページが弾かれてループする  
例：`matcher: ["/admin/((?!login).*)"]`

### 2.3 セッションで `shopId` を持つ意味
- クライアント送信のshopIdを廃止できる
- その結果、**他店舗のデータ更新**をサーバ側で確実に防げる

### 2.4 `tsx` を使う理由
- `ts-node/esm` は環境差で落ちやすい
- `npx tsx` は開発用スクリプト実行が安定しやすい
