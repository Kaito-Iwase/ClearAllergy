# AI報告・ハーネス・PRの読む負担を減らす

2026-11-14の設計判断。比較元はmain `7b9933af23c1fb834a6b0ad1b169484995040795`。この日付の作業差分として実装し、mainへの採用・配備とは区別する。現在の運用規則は[報告の書き方](../../guide/maintenance.md#reporting)、コマンドは[自律開発の手順](../../agentic-development.md)を参照する。

## 問題と本人に合わせた判断

ユーザーは「出力に対する認知負荷がかなり高い」と述べ、対象を「AIの作業報告・ハーネス・PRなど全体」と指定した。さらに実装前の敵対的レビューの反復を求めた。短い文章だけを求めた、と限定して解釈しない。

確認した現状は、AGENTSの完了報告6項目、PRテンプレート6節、runnerの全JSON出力が並行して存在すること。[直近のPR #152](https://github.com/Kaito-Iwase/ClearAllergy/pull/152)は取得時点で3ファイルの変更に本文54行・3,033文字を使い、初回候補・最終候補・マージ後の証拠が全展開されていた。この1例だけで全報告の質や本人の読解時間を評価はできない。

このプロダクトでは、確認済みと不確実な状態を取り違えないことが重要。開発時にも、ローカル成功、CI、配備、利用者の理解を一つの「完了」へ丸めない。本人が毎回ログを再構成する代わりに、エージェントが結果・必要な判断・次の操作を先に整理する方式を選んだ。

## 公開事例から採るもの

以下は一次資料で確認した実践からの設計上の転用であり、ClearAllergyや本人への効果を実測した証拠ではない。

| 事例 | 資料で確認した考え方 | 今回の採用と限界 |
| --- | --- | --- |
| [OpenAI: Harness engineering](https://openai.com/index/harness-engineering/)（2026-02-11） | 巨大な一枚の指示書ではなく、小さい入口から必要な文書へ進む段階的な情報開示 | 人向け報告も短い入口と詳細証拠に分ける。原典は主にエージェントの理解を扱い、人間の負荷削減を直接証明するものではない。全面的な文書再編・追加CIは採らない |
| [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)（2025-11-26） | セッションをまたぐ進捗記録と段階的な実装で、状態を再構築できるようにする | 詳細証拠と再開に必要な状態は既存report/PR/Issueに保持する。新しい進捗ファイルを毎回増やす方式は採らない |
| [Google SRE: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)（2026-11-14閲覧） | 人の注意を消費する通知は、意味があり行動につながるものへ絞る | 判断が必要な対象と次の担当を明確にし、変化のない状態・成功ログの反復を避ける。オンコール向けの実践を日常開発へ転用しており、通知基盤は導入しない |

## 比較した案

| 案 | 判断 |
| --- | --- |
| 全文を単に短縮する | 不採用。失敗や未確認の対象を落とすと、短くても判断を誤る |
| dashboardや新しい報告ファイルを追加する | 不採用。見る場所、更新作業、状態の同期が増える。既存の記録を使う |
| 判断項目をすべてユーザーへ確認する | 不採用。技術作業や許可済み事項まで判断負担を戻す |
| 結果・判断/次の操作を先頭に揃え、詳細は必要時に開く | 採用。失敗・必須未検証・重要リスクは先頭に残し、成功時の詳細を中心に分離する |

## 実装前の敵対的レビュー

実装履歴を渡さない読取専用レビューを2回実施し、各回の指摘で案を修正してから実装へ進んだ。これはGitHubのApproveや本人の使いやすさ評価ではない。

| 反証 | 採った修正 |
| --- | --- |
| 既定stdoutを短文へ変えると、repo外のJSON利用者が壊れる | 既定JSON維持。人向け手順に `--format summary` を付ける |
| 全コマンド成功でも差分検査が失敗する | `diffCheck` の失敗も要約に出す |
| 保存先を交換された場合、表示したファイルパスが証拠を指さない | `publicationSafe:false` では通常の証拠パスを出さず、証拠として使えないと表示 |
| 詳細の再評価時にsnapshotが15分で失効する | completionの保留理由はその場に全件表示。再評価には期限があると記載 |
| 保留理由1件が複数の未達条件を表す、または残り条件が未判定 | 「検出した保留理由」と記載し、完了計画が確認できない場合は残り条件も未判定と表示 |
| 同じ理由が人間判断と技術的ブロッカーの両方を含む | runnerだけで本人の操作要否を断定しない。エージェントが原典を照合する |
| 既にCLOSEDのIssueが未完了のように見える | 「既にCLOSED・今回close操作なし」とし、既存記録の確認を案内 |

## 変更範囲と確認方法

- AI報告は[AGENTS](../../../AGENTS.md)から[報告規則](../../guide/maintenance.md#reporting)へ案内する。PRは[テンプレート](../../../.github/pull_request_template.md)の短い冒頭と折りたたみ詳細を使う。
- runnerの判定・保存JSON・終了コードを維持し、`scripts/agent-harness-output.mjs` に表示だけを分離する。新しい依存・サービス・検証gateは追加しない。
- `tests/agent-harness.test.ts` でJSON互換性、候補なし、期限切れ、判断待ち、多数の保留、既存CLOSED、未判定、失敗工程、検証対象/保存先の不整合、Node差、入力の制御文字、不正なformatを確認する。通常のlint・型検査・全テスト・buildも維持する。
- 製品画面・アレルゲン状態・認証/認可・DBの意味は変更しないため、product/rules/architectureや画面のブラウザ回帰は今回の変更対象外。READMEの既存入口から更新規則へ到達でき、読む順番の変更は不要。

正常な代表出力が短くなり、失敗時に必要情報が残ることは自動検査できる。ただし行数・文字数は代理指標にすぎず、本人の認知負荷が改善したと断定しない。次の実作業で、冒頭だけで現在地・本人の操作要否・次の担当が分かるか、詳細を探し直す負担がないかを確認する。新たな定期アンケートや計測基盤は設けない。
