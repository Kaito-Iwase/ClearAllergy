# 利用者や店舗に生じ得る被害と、その原因になる状況

[研究資料の入口](../README.md) · [書き直す前の原稿](../originals/20261015-ja-readability/losses-hazards.md.txt) · [現在の状態・公開・権限のルール](../../guide/rules.md)

この文書では、ClearAllergyの情報や操作が、どのような経路で利用者や店舗の被害・不利益につながり得るかを整理します。2026-09-28の研究原稿を、日本語で読み進められるように説明し直したものです。現在残っている不具合や、実際に起きた事故の一覧ではありません。

## 分析の方法と、ここで分かることの限界

原稿の分析は、STPA（システム全体の動きや人の操作から、事故につながる状況を洗い出す安全分析手法）の考え方を参考にしています。出典は[参考資料X10](../03-evidence-register.md)にあるMITの解説です。原稿の「STPA-inspired」は、この手法を参考にしたという意味です。複数の専門分野の人が参加する検討会や厨房での実地観察は行っておらず、STPAの手順全体を実施した分析でもありません。

ここでは、被害がどれほど重大になり得るかを考慮します。ただし、各問題が起こる確率は算出していません。数値に基づく危険度の順位も付けていません。

研究時点のClearAllergyは、架空データを使うプロトタイプ（機能や使い方を確かめるための試作品）です。身体への被害は、この試作品の想定用途の外にあります。以下では、将来の実利用だけでなく、試作品が誤って実際の飲食判断に使われる場合も含めて検討しています。

## この文書の読み方

まず「避けたい被害・不利益」をL01〜L04として示し、次に、それらにつながる状況と操作例をH01〜H10として説明します。

被害・不利益は原稿のLossに当たります。危険につながる状況はHazardに当たり、ここでは、システムの状態や条件に周囲の悪条件が重なると被害に至り得る状況を指します。「被害」と「それにつながる状況」を分けて読むための呼び方です。

各項目の末尾には、関連する被害のIDと、防ぐための条件の参照先を残しています。ID（文書間で同じ項目を指すための識別番号）のL・H・SC・SRなどは、[条件・要件の一覧](safety-constraints.md)や[根拠と要件の対応表](../traceability-matrix.md)と照合するために使います。条件や要件には当時未承認だった案も含まれるため、現在の採用状況は[現行ガイド](../../guide/rules.md)と[検証記録の入口](../../guide/verification.md)で確認してください。

## 避けたい被害・不利益

- <a id="l01"></a> **L01：誤った飲食判断に寄与し、身体への被害につながること。** 利用者が表示を誤って理解し、その情報をもとに飲食を判断する場合を含みます。
- <a id="l02"></a> **L02：必要な情報を得られず、利用機会を失うこと。** 店舗や料理を必要以上に避けてしまう場合も含みます。
- <a id="l03"></a> **L03：店舗や利用者の情報・権限が侵害されること。**
- <a id="l04"></a> **L04：問題の影響が長引くこと。** 原因を特定できない、誤りを修正できない、または復旧できない場合を含みます。

## 被害につながる状況と操作例

以下は研究時点の候補です。原因になり得る条件を説明するための例であり、通常の保存経路で発生した事実や、現在も未修正であるという主張には読み替えません。

<a id="h01"></a>

### H01：アプリが認識できない状態の値を「含まない」側に扱ってしまう

アプリが認識できない状態の値を受け取ったときに、不明な状態として扱わず、`FREE`（原材料に含まないことを表す値）側の判定へ進めてしまうケースです。

原稿は、文字列を状態の型とみなす処理と、判定できない場合に`FREE`側へ進む処理を挙げています。[局所実験EX01](../03-evidence-register.md)は、実際の食品ではなく、作った入力値を関数へ渡してこの問題を調べた記録です。将来、列挙型（保存できる状態の候補を定めた型）を変更したり、外部データを取り込んだりした際に、定義と入力値が食い違う場合も検討対象です。

この誤った判定が飲食判断に使われると、身体への被害（L01）につながるおそれがあります。ただし、通常の入力経路にある防御と、実験で作った値が入る経路は区別します。防御については末尾の[反証・抑制条件](#counter-scenarios)を参照してください。

関連する被害：[L01](#l01)。対応する条件：[SC01 / SR-SEM-001](safety-constraints.md)。

<a id="h02"></a>

### H02：必要な情報が欠けたメニューや、品目定義と食い違うメニューを公開する

必要な情報が欠けたメニューを公開したり、アレルゲンの品目マスタ（対象品目の共通定義）と登録内容の食い違いを見落としたりするケースです。

検討するのは、API（画面などからアプリの処理を呼び出す窓口）やデータベースの検査を迂回して更新する場合、品目マスタを変更する場合、または公開フラグだけを見て公開できると判断する場合です。公開フラグとは、公開中かどうかを保存する値です。その値だけでは、必要な情報が揃っているかまでは分かりません。

これらは、誤った飲食判断による身体への被害（L01）や、必要な情報が得られないことによる機会損失（L02）につながるおそれがあります。既存の公開判定などがこの問題を抑えることも、末尾の反証・抑制条件に残しています。

関連する被害：[L01](#l01) / [L02](#l02)。対応する条件：[SC02 / SR-PUB-001](safety-constraints.md)。

<a id="h03"></a>

### H03：権限のない相手や、本人確認が不確かな相手に変更を許可する

対象店舗の所有者ではない相手や、本人確認が不確かな相手に、データの変更を許可してしまうケースです。

たとえば、要求に含まれる対象IDを別のデータのIDへ差し替える場合を考えます。また、サーバーが権限を確認してから実際に書き込むまでの間に所有関係が変わる場合や、メールアドレスだけを根拠に本人や権限を判断する場合も検討対象です。

不正な変更によって誤った情報が飲食判断に使われれば身体への被害（L01）につながり得ます。店舗や利用者の情報・権限が侵害されること（L03）も、別の被害として扱います。

関連する被害：[L01](#l01) / [L03](#l03)。対応する条件：[SC03 / SEC-OWN-001 / SEC-ID-001](safety-constraints.md)。

<a id="h04"></a>

### H04：古い入力で訂正を上書きする／保存結果が不明なのに「未保存」と伝える

この項目では、次の2つのケースを分けて考えます。

**先に保存した訂正が、古い入力で上書きされる場合。** 同じメニューを2つのタブで開いている場面を考えます。店舗担当者が片方のタブで情報を訂正して保存した後、もう片方の古いタブから全品目の状態を保存すると、先に行った訂正を元に戻してしまうおそれがあります。同じ担当者が両方のタブを操作する場合にも起こり得る条件です。

**保存できたか不明なのに、画面が「保存されていない」と伝える場合。** データベースへの保存が確定した後、その後の処理でエラーが起きる場合があります。ここでサーバーがHTTP 500（サーバー側の処理失敗を示す応答）を返し、画面が単純に「未保存」と案内すると、担当者が作成要求をもう一度送るおそれがあります。原稿の「再POST」は、この作成要求の再送を指します。

保存済みか確認できない状態と、保存されなかったことが分かっている状態は区別する必要があります。正しい訂正が失われたり、誤った案内に基づいて再送されたりすれば、誤った飲食判断（L01）や、訂正・復旧の遅れによる影響の長期化（L04）につながるおそれがあります。

関連する被害：[L01](#l01) / [L04](#l04)。対応する条件：[SC04 / DR-CON-001 / DR-OUT-001](safety-constraints.md)。

<a id="h05"></a>

### H05：以前の根拠を、現在の食品内容を確認した証拠として扱う

レシピや仕入れが変わったことが報告されず、以前の確認内容のまま公開されるケースです。

`updatedAt`（一般的なデータ更新日時）が新しくなっただけなのに、食品の内容も再確認されたように扱う場合や、何を確認したかの記録がない場合も含みます。データを更新したことと、現在の食品内容を確認したことは別です。

古い根拠に基づく表示は、誤った飲食判断（L01）につながるおそれがあります。確認した内容を追えなければ、問題の修正や復旧が遅れて影響が長引くこと（L04）も考えられます。

関連する被害：[L01](#l01) / [L04](#l04)。対応する条件：[SC05 / SR-REV-001 / DR-PROV-001](safety-constraints.md)。

<a id="h06"></a>

### H06：公開停止や訂正が届かず、利用者の画面に古い情報が残る

店舗担当者がメニューを非公開にしたり情報を訂正したりしても、利用者には以前の情報が表示され続けるケースです。

原稿は、ISR（保存済みのページを再生成しながら配信する仕組み）を使う場合、データベースへ直接修正を加える場合、利用者がタブを開いたままにする場合を挙げています。さらに、別々のデータ取得処理が異なる時点の情報を読み、ひとつの表示に混ざる場合も検討しています。これらはそれぞれ経路が異なり、サーバーのデータを直すだけで、既に開いた画面も必ず直るとは限りません。

古い情報が飲食判断に使われること（L01）や、公開停止・訂正が届かないため影響が長引くこと（L04）につながるおそれがあります。ISRは研究時点の検討対象であり、この説明から現行アプリも同じ配信方式だと判断しないでください。

関連する被害：[L01](#l01) / [L04](#l04)。対応する条件：[SC06 / SR-FRESH-001](safety-constraints.md)。

<a id="h07"></a>

### H07：登録内容が正しくても、表示・伝達・対象の取り違えで誤解が生じる

登録されたデータ自体に誤りがなくても、利用者が画面を読み違えたり、人から人へ伝える途中で意味が変わったり、別の人の設定を使ったりするケースです。

原稿は、緑色を見ただけで「安全」と受け取ることや、`STORE_HANDLED`（店舗内の取扱い情報から表示する補足）を「厨房での確認が済んだ」という意味に取り違えることを挙げています。また、研究時点で対象としていた29品目以外の食物があること、代理で設定した人と飲食する本人の対象が食い違うこと、スクリーンリーダー（画面の内容を音声などで伝える支援技術）を使った際の伝わり方も検討対象です。

これらは、誤った飲食判断による身体への被害（L01）と、必要以上に避けることによる機会損失（L02）の両方につながるおそれがあります。色や表示だけで食品の安全性を保証するという意味には広げません。

関連する被害：[L01](#l01) / [L02](#l02)。対応する条件：[SC07 / UX-COMP-001 / UX-A11Y-001](safety-constraints.md)。

<a id="h08"></a>

### H08：下書きの画像や、削除した料理の画像を想定外の相手に提供する

メニューを非公開にしたり削除したりしても、画像が同じ範囲で非公開・削除になるとは限らないケースです。

原稿は、公開型のBlob（画像ファイルを置く保存先）へのアクセスがメニューの公開状態とは独立していることと、どのメニューからも参照されなくなった画像が保存先に残ることを挙げています。画像の参照を消すことと、画像そのものへのアクセスを止めることを分けて検討します。

想定外の画像提供による情報の侵害（L03）や、問題の特定・回収が難しくなることによる影響の長期化（L04）につながるおそれがあります。

関連する被害：[L03](#l03) / [L04](#l04)。対応する条件：[SC08 / SEC-ASSET-001](safety-constraints.md)。

<a id="h09"></a>

### H09：問題の検知・公開停止・結果の照合を行えない、または対応が遅れる

問題が起きても運営担当者が気付けない場合や、必要な公開停止・結果の照合を行えない場合、または対応に時間がかかり過ぎる場合です。

原稿は、監査記録（誰がどの操作をしたかを後からたどるための記録）の保存に失敗しても本来の処理を止めない方式、通知や復旧の仕組みを調査で確認できていないこと、外部サービス側で処理が完了したか分からないことを挙げています。操作したつもりでも、その結果や対応の経緯を確かめられるとは限りません。調査で未確認だったことと、実際の運用でその仕組みが存在しないことは区別します。

必要な対応が遅れると、誤った飲食判断（L01）や、影響の長期化（L04）につながるおそれがあります。

関連する被害：[L01](#l01) / [L04](#l04)。対応する条件：[SC09 / OR-INC-001](safety-constraints.md)。

<a id="h10"></a>

### H10：手元で検証したものとは異なる構成を、配備先で動かしてしまう

開発担当者が手元の環境で検証できたと思っていても、配備先では異なるコード・設定・データベース構造が動いているケースです。

原稿は、必要なデータベース構造の変更が適用されていないこと、秘密情報がブラウザ側のコードへ入ること、古いパッケージが使われること、アクセス先に応じてページを保護する処理（原稿のproxy）の条件が想定と異なることを挙げています。検証した構成と実際に動く構成が一致しなければ、検証結果をそのまま配備先の根拠にはできません。

誤った情報が使われることによる身体への被害（L01）、情報・権限の侵害（L03）、原因特定や復旧が難しくなることによる影響の長期化（L04）につながるおそれがあります。

関連する被害：[L01](#l01) / [L03](#l03) / [L04](#l04)。対応する条件：[SC10 / OR-REL-001](safety-constraints.md)。

## 操作を4つの観点から点検する

原稿では、危険につながり得る操作を次の4種類で点検しています。これは原稿のUnsafe control actionに当たります。

1. **必要な操作をしない。** たとえば、変更を報告しない、古い確認を無効にしない場合です。
2. **その状況で行うと危険につながる操作をする。** たとえば、必要な情報が揃っていないのに公開する場合や、対象や内容を取り違えて更新する場合です。
3. **順序や時刻が適切でない。** 古い入力を後から取り込む場合や、保存確定後の処理で失敗する場合を検討しています。
4. **操作や表示が長過ぎる、または短過ぎる。** 古い表示を長く残す場合や、必要な警告が早く消える場合です。

データが正しくても画面によって誤解が生じる場合と、人同士の伝達で誤りが生じる場合も分析から外しません。

<a id="counter-scenarios"></a>

## 危険の候補を過大評価しないための反証・抑制条件

原稿にある次の条件も、危険の候補と併せて読みます。

- **H01には通常経路の防御がある。** APIの入力検査、Zod（入力値が決めた形式に合うかを検査するライブラリ）、データベースの列挙型は、不正な値が通常経路から入ることを防ぐ仕組みです。局所実験EX01の結果だけで、通常経路でも同じ問題が起きるとは判断しません。
- **H02を抑える既存の仕組みがある。** 共通の公開判定関数と、保存の確定時などに整合性を検査する遅延トリガー（データベース側で検査の実行を遅らせる仕組み）が挙げられています。
- **担当者が1人でも、2つのタブは使える。** H04の条件は複数担当者に限りません。ただし、どの程度の頻度で起きるかは測定していません。
- **架空データの試作品と、実際の食品被害には距離がある。** 本物の食品を扱わない試作品であれば、表示から身体への被害（L01）へ直接つながる経路は限定されます。

これらの危険の候補を、実運用で起きた事故として記載しません。安全条件や未確認事項を残すことと、発生実績・発生確率を確認したと主張することは別です。
