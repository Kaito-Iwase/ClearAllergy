# ClearAllergy向け：Big Tech一次資料から採る、小さなコンテキスト整備

調査日：2026-10-14（UTC）

## 結論

CAにはすでに `app / features / components / lib / prisma` と、root `AGENTS.md`、guide / rules / change-map / research / verification がある。この前提なら、追加の大きな仕組みより、**入口を短くし、正本を決め、変更と検証のつながりを直す**のが先である。

推奨するのは以下の6点。1〜4と6は既存文書の小修正で始め、5の自動化は既存チェックを調べてから判断する。文書が増えること、AIが文書を読み込むこと、リンクチェックが通ることだけでは、実装や回答の正しさは保証されない。

このレポートは公開一次資料の調査結果である。CAの構成は依頼元から受けた既存調査を前提としており、この調査ではCAのcheckout確認、コマンド実行、CI検証は行っていない。以下のCAへの適用、工数、成功条件は提案であり、各社の実績数値ではない。

## 根拠の読み分け

- **社内事例の記録**：Googleの『Software Engineering at Google』は、当時の社内経験を説明している。2020年の記録を、そのまま2026年の全組織共通ルールとは扱わない。
- **公式推奨**：Google Style Guides、VS Codeの製品文書は公式な推奨・仕様である。全社員がその方式で仕事をしている証拠とは区別する。
- **公開リポジトリで確認できる実践**：`microsoft/vscode` と `facebook/docusaurus` の指示ファイルは、そのプロジェクトが公開している実物。会社全体へ一般化しない。
- **製品機能**：Docusaurusのリンク検出、Google Cloudのgrounding、Microsoft Foundryの例は製品機能・利用例。CAに製品そのものを導入する必要性とは別である。

## 1. 文書を小さく保ち、コードと同じ変更で直す

**判定：採用。既存文書の整理を優先。**

### 一次資料の事実

Googleの公式文書ガイドは、少数で新鮮な文書、コードと同じCLでの更新、古い・重複する情報の削除、共通知識の複製よりリンクを推奨している。設計文書も実装後は意思決定の記録として扱い、不完全な現行仕様書にしない。[Google Documentation Best Practices](https://github.com/google/styleguide/blob/9b15a1d71f9591fcb3f30f1e4f4dc77e94e7eef0/docguide/best_practices.md)

これは公式ガイド。参照ファイルの最終変更コミット日時は2025-01-17 UTCで、初出日ではない。

### CAへの適用

- PRの確認項目を1つだけ置く：「この変更でguide / rules / change-map / verificationの更新は必要か。必要なら同じPRに含め、不要なら理由を1行で書く」
- すべてのコード変更で文書を増やす必要はない。配置、APIの約束、検証手順、重要な判断が変わる場合を対象にする。
- `research` の案を採用したら、採用済みの規則だけを `rules` 等の正本へ反映する。調査過程や却下案を現行ルールとして読ませない。
- Next.js・TypeScript・Hono・Prismaの一般的な説明は公式資料へリンクし、CA固有の使い方・制約・理由だけを残す。

**初期費用目安**：30〜60分。以後は対象PRごとに数分。確認範囲が大きい場合は分割する。

**観測できる成功条件**：次の文書に影響する変更3件で、関連文書が同じPRに含まれるか、不要理由が残る。誤った説明を追記で埋めず、削除・置換できている。

## 2. 同じ事実に正本を1つ置き、直す人と契機を決める

**判定：採用。専用ポータルや新しい管理基盤は不要。**

### 一次資料の事実

Googleの2020年刊行書籍は、文書のowner、正本の指定、ソース管理・レビューへの統合を説明する。社内wikiで重複や陳腐化が起き、コードの近くに文書を置くg3docと既存の開発手順を使うことで改善したという社内事例がある。またownerと最終確認日を記す方法も紹介している。[Documentation章](https://abseil.io/resources/swe-book/html/ch10.html)、[刊行時期の説明](https://abseil.io/resources/swe-book)

### CAへの適用

正本は「ファイルを1つにする」という意味ではなく、**同じ情報を何箇所も手で更新しない**という意味にする。

| 情報 | CAでの正本候補 | 他の文書での扱い |
|---|---|---|
| 実在するスクリプトと実行内容 | `package.json` と実際のCI定義 | verificationから参照する |
| データ構造の実装 | Prisma schema・migration・関連コード | guideには役割と入口を示す |
| APIの実際の振る舞い | Hono実装・schema・関連テスト | rulesには守るべき契約と理由を記す |
| 設計上の約束・境界 | 既存rules | AGENTSやguideでは重複せずリンク |
| 変更箇所の探し方 | 既存change-map | 全ファイル一覧にせず、入口と確認先を示す |
| 未採用案・外部調査 | 既存research | 状態・確認日・一次資料リンクを付ける |

コードが正本というだけで、現在の不具合を正しい仕様と認定しない。契約と実装が食い違った場合は、食い違いを明示して判断する。

ownerは少人数なら「この領域の変更者が更新し、通常のレビュアーが確認」でよい。全ページの手動タイムスタンプは不要。外部情報や運用手順など古さが問題になる文書にだけ確認日を置く。

**初期費用目安**：45〜90分。維持費は通常のレビュー内。

**観測できる成功条件**：任意の規則・実行方法について、2分以内に正本へたどり着ける。同じ規則の矛盾した複製が0件。コマンド変更時に、人手で直す独立した説明が1箇所で済む。

## 3. root AGENTSを短い入口にし、必要な文脈だけを読む

**判定：採用。細かな階層化やskills追加は、反復する問題がある場合まで保留。**

### 一次資料の事実

MicrosoftのVS Code公開リポジトリでは、root `AGENTS.md` は詳細なoverview・architecture・guidelines・validationを別の指示ファイルへ案内する短い入口になっている。これは公開プロジェクトの実物である。[AGENTS.md：2026-08-07コミット版](https://github.com/microsoft/vscode/blob/109997242d097eb51b87329a514dc0adad413337/AGENTS.md)

VS Code公式ガイドは、既存ファイルを尊重し、重複を除き、コードから確実に分からないプロジェクト固有の判断に絞ること、実際に指示が適用されたか確認することを勧める。範囲別の指示は任意の追加段階で、利用するagentの種類により発見・適用ルールが異なる。[Configure AI for your codebase：2026-10-07表示](https://code.visualstudio.com/docs/agents/guides/customize-copilot-guide)

### CAへの適用

root AGENTSには次だけを残す。

1. CAの目的と技術構成を短く示す
2. 最初に読むguideとrulesの入口
3. 作業別にchange-map / verification / researchを読む条件
4. 実在する検証コマンドの参照先
5. 不明点・未実行検証・規則と実装の不一致を報告する約束

API作業ならHonoの入口・該当feature・Prisma・関連テストへ、UI作業なら画面・feature・共有component・関連検証へ進めるよう、既存change-mapを整える。全docsの全文を毎回注入しない。

`features/*/AGENTS.md` 等を機械的に大量作成しない。複数領域で異なる指示が実際に必要になったときだけ追加し、CAで使っているagentがその場所を読むことを新しいセッションで確認する。

**初期費用目安**：30〜60分。領域別指示の追加は別途15〜30分/領域。

**観測できる成功条件**：代表的なUI・API変更の各1件で、必要文書の読み込み、配置、既存パターンの利用が確認できる。全文読込量が減っても、誤配置や重要規則の見落としが増えない。単に「読んだ」と答えたことは合格としない。

## 4. 「検証する」を、実在するコマンド・対象・結果へ落とす

**判定：採用。コマンドやテスト基盤を他社からコピーしない。**

### 一次資料の事実

VS Codeの実物の指示は、変更範囲・リスクに合わせた検証、既存診断の利用、対象を絞ったテスト、関連入力が変わらない成功結果の再利用、具体的なコマンドを記す。[VS Code Copilot Instructions：2026-10-12コミット版](https://github.com/microsoft/vscode/blob/c480e9e49e2a116c458518ecbdec56d50e4af3d2/.github/copilot-instructions.md)

Metaの公開Docusaurusリポジトリも、サイトbuild・typecheck・単体テスト等の実行コマンドと、snapshotを無検討で更新しないことを指示している。[Docusaurus AGENTS.md：2026-10-01コミット版](https://github.com/facebook/docusaurus/blob/1a6ff4303d24cdb68959ca567a4d8226d22fb5e1/AGENTS.md)

両者は実際の公開プロジェクトの規約で、全社共通運用ではない。また最終検証の範囲は同一ではない。CAの規模、CI、変更リスクに合わせて決める。

### CAへの適用

- 既存verificationに「どこで／何を／いつ実行するか／何が確認できるか」を短く書く。
- 実際の `package.json`、lockfile、CIにあるコマンドを確認して記す。`npm test`、`pnpm test`、`lint`、`typecheck` 等を存在確認なしに作り話で記載しない。
- API・入力検証・認可・DB変更は関連テスト、UI変更は型検査等に加え必要な画面確認、schema変更は既存のPrisma検証・migration手順へ結びつける。これは検証候補であり、CAにすべてのテストが現存するとは主張しない。
- 完了報告を「実行したコマンド／対象commitまたは差分／成功・失敗／未実行と理由」にそろえる。未実行を成功扱いしない。
- 繰り返す重要規則は、可能なら既存lint・型・testで表現する。文書の注意書きだけに依存しない。

**初期費用目安**：45〜90分。既存の検証手順が壊れている場合の修理やテスト新設は別見積もり。

**観測できる成功条件**：新しい作業環境で文書どおりに代表チェックを1回実行できる。完了報告に、存在しないコマンドや未実行の成功宣言がない。対象を絞った確認と全体チェックを区別できる。

## 5. 文書のリンク・参照先を機械確認する。ただし文書サイトは急がない

**判定：原則は採用。自動化は既存CIに小さく追加できる場合に採用。Docusaurus新規導入は保留。**

### 一次資料の事実

Docusaurus公式仕様では、`onBrokenLinks` はproduction buildで検出した壊れたリンクを既定でerrorにする。一方、anchorは既定でwarningであり、すべて同じ厳しさではない。[Docusaurus 3.10.2 config](https://docusaurus.io/docs/api/docusaurus-config#onbrokenlinks)

これはDocusaurusの製品機能であり、任意のMarkdownや外部URLがすべて検証されるという意味ではない。Metaの公式2019-01-02記事は、Docusaurusが当時複数の同社OSSプロジェクトに利用されていたことを記録しているが、現在の全社文書基盤の証拠にはしない。[Metaの2018年振り返り](https://engineering.fb.com/2019/01/02/open-source/open-source-2018/)

### CAへの適用

- 最初はroot AGENTSからリンクする文書、guide、change-mapの相対パスと参照先ファイルの実在を点検する。
- 自動化する場合は、既存CIの1ジョブまたは既存docs checkへ統合する。新しいサイト、公開URL、検索indexは作らない。
- 見出しanchorの検査をするなら、CAの実際のMarkdownレンダリング規則に合わせる。雑な正規表現で誤検知が多いなら対象を狭める。
- 外部URLの一時的な失敗やrate limitで毎PRを止める設計は避ける。まずローカル参照の確定的な検査を優先し、外部リンクは変更時の確認から始める。

**初期費用目安**：手動整理15〜30分。小さなCI検査を追加する場合は1〜3時間。新規サイトの導入・運用はこの費用に含めず、当面行わない。

**観測できる成功条件**：存在しない相対リンクを1つ意図的に作るとチェックが失敗し、修正すると成功する。重要な入口のリンク切れ0件。チェックの追加時間と誤検知件数を残し、過大なら範囲を縮める。

## 6. 事実・提案・未確認を区別し、出典まで戻れるようにする

**判定：採用。RAG・vector DB・grounding製品の導入は保留。**

### 一次資料の事実

Google Cloudはgroundingを、出力を検証可能な情報源につなげ、出典リンクで監査しやすくするものと説明している。[Grounding overview：2026-10-13更新](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/overview)

Microsoft Foundryの公式例は、取得情報で不足するなら答えを作らず分からないと伝える指示を示している。同時に、groundednessの判定と、判定後に処理を続行する設定を別に扱っている。[Foundry middleware：2026-09-10更新](https://learn.microsoft.com/en-us/azure/foundry/how-to/develop/langchain-middleware#improve-grounding-with-a-stricter-prompt)

いずれも製品説明・サンプルであり、文書に一文追加すれば誤回答を防げるという実証ではない。

### CAへの適用

- `research` の各結論に、一次資料URL、確認日、適用対象version、状態（採用／検討中／却下／未確認）を付ける。
- コードに関する断定にはファイル・symbol・testへの参照を付ける。調査記録で再現性が必要ならcommitも残す。普段のナビゲーションをすべて過去commit固定にして、現行コードから切り離さない。
- 文書上の「期待する仕様」と「現在確認した実装」を明確に分ける。相違があれば勝手に片方へ合わせず、確認点として残す。
- 商品・原材料・アレルゲン等の外部データを扱う場合、未確認・出典なしを確認済みへ変換しない。これはCAへのデータ品質上の提案であり、既存実装がそうなっているという指摘ではない。
- AIへの完了条件に「出典にないこと、実行していないことは推測で埋めず区別する」を短く書く。特に重要な状態変換はtestとreviewでも検証する。

**初期費用目安**：書式整理30〜60分。各調査メモの新規記入は数分。データモデル・テスト変更が必要なら別途判断する。

**観測できる成功条件**：直近の重要な調査結論5件が出典またはコードへ追跡できる。未確認データを使うテスト入力を与えたとき、勝手な確定値を出さず不足が報告される。「引用がある」だけで正しいと扱わず、引用先が主張を支えているか確認する。

## CAで今やる順番

1. 既存guide / rules / change-map / verificationの重複・矛盾・リンク切れだけを一覧化する。
2. 正本を決め、root AGENTSからの入口を短くする。ファイル名・階層の全面変更はしない。
3. 検証コマンドを実物と突き合わせ、成功・失敗・未実行の報告形式をそろえる。
4. 代表的な小変更を同じ条件で試す。モデル、agent、ツール、タスクをできるだけそろえ、誤配置、不要な探索、誤コマンド、修正指示の回数を比べる。
5. 実害のある失敗が残った箇所にだけ、小さな追加指示か自動チェックを入れる。

最初の文書整理は合計おおむね半日〜1日を上限の目安とする。これはCAの実ファイル数や品質を検査した見積もりではないため、初回点検後に調整する。既存チェックの故障修理、実装変更、新規テスト基盤は含めない。

## 今は採らないもの

- **保留**：Docusaurus等の新しい文書サイト。外部向け公開、複数version、多言語文書などの明確な要件が出たら再検討する。
- **保留**：RAG、vector DB、MCP、独自の文脈配信サービス。少数の既存文書をリンクと検索で扱える間は運用対象を増やさない。
- **保留**：領域別AGENTSやskillsの大量作成。少なくとも反復する誤りと独立した規則が確認されてから。
- **不採用**：全docsをroot AGENTSへ複製すること、一般論のチェックリストを大量追加すること、企業規模の承認フローやモノレポ構成をそのまま輸入すること。
- **不採用**：「文書を書いたから正しい」「AIが指示を読んだから遵守した」「リンクが生きているから内容も新しい」という合格基準。

## 参照の固定方法と限界

公開repoの3ファイルとGoogle guideはGitHub APIでファイル別の最終変更commitを取得し、そのcommit版の本文も読み直した。上記のリンクは固定commitを使っている。commit日時はそれぞれの採用・導入開始日を意味しない。

製品文書は表示されている更新日・versionと調査日を併記した。全社の非公開運用は確認していない。また、これらの資料からCAでの具体的な生産性向上率や誤り削減率は推定できない。採否は小さな比較実験と、実際の手戻り・検証結果で判断する。
