# ClearAllergy向け：日本企業の一次資料から選ぶ、人間＋AIの開発コンテキスト整備

調査日：2026-10-14。公開された技術記事・公式アカウントの資料を確認。以下は採用案であり、ClearAllergyへの変更は行っていない。

## 結論

ClearAllergyには、既存の `AGENTS.md` と `guide / rules / change-map / research / verification` を活かす小さな整理が合う。まず実施するのは次の5点。

1. **入口を短くする。** AGENTSにはプロジェクト固有の必須制約と「どの作業ならどこを見るか」だけを残す。
2. **同じルールの正本を1つにする。** 人間用・AI用・ツール別で内容を複製しない。
3. **変更箇所と確認方法を結ぶ。** change-mapから実在するコード、規則、検証手順へ到達できるようにする。
4. **現状と履歴を分ける。** 現行仕様、採用済み判断、未採用の調査、特定時点の検証結果を混ぜない。
5. **コード変更と文書変更を同じレビューで確認する。** 判定できることはlint・型チェック・テスト等に任せ、人間は仕様・例外・判断理由を確認する。

このために新しいアーキテクチャ層、文書管理サービス、大規模なエージェント基盤を導入する必要はない。

### 前提と限界

- 提示された構成は Next.js 16 / React 19 / TypeScript / Hono / Prisma と `app / features / components / lib / prisma`。本調査単体ではClearAllergyの各ファイル本文、実行コマンド、CIを監査していない。
- 以下の役割分担は提案。現行ルート配置や依存方向を既成事実として断定せず、コード監査結果と突合して確定する。
- 事例は各記事で紹介されたチーム・プロダクトのもの。企業全体の標準とも、2026年10月現在も不変の運用とも扱わない。
- 所要時間はClearAllergyへの小規模適用を想定した独自概算。各社の実測値ではなく、項目間で重複するため単純合算しない。

## 1. LINEヤフー：常駐コンテキストを絞り、作業に必要な知識へ案内する

**一次資料**：[LINE iOSアプリ開発を高速化するClaude Code基盤の設計思想](https://techblog.lycorp.co.jp/ja/20260119a)（2026-01-19、モバイルデベロッパーエクスペリエンスチーム、giginet）。

**確認できた実践**：LINE iOSでは常駐メモリを前提知識と開発手順に絞り、記事時点で英文約2400文字・600 tokensとした。詳細は必要時に読むRulesやSkillsへ分け、形式や規約を機械的に扱える部分はスクリプト・linterで支える。探索とビルドの失敗が導入の動機だった。対象は大規模iOS開発の基盤で、一般的な小規模開発の必須構成ではない。[本文](https://techblog.lycorp.co.jp/ja/20260119a)

**ClearAllergyで採る機構**

- AGENTSの本文は、目的、現行の実装上の重要制約、タスク別参照先、変更後の確認先に限定する。
- `change-map` を「画面表示を変える」「APIの入力・出力を変える」「データモデルを変える」「共通UIを変える」という作業起点の索引にする。
- 各行は、入口となる実在パス、合わせて調べる場所、参照規則、確認方法の4点程度にする。リポジトリの全ファイル一覧は再掲しない。
- Next/React/TypeScriptの一般解説を増やすより、「このプロジェクトではどこを見るべきか」「既存実装と異なる点は何か」を記す。
- コマンドの実体はpackage scriptsやCIを正本とし、検証文書には目的と実行条件を記す。

**移さない機構**

- LINEの巨大iOSビルドを前提にした「フルビルドを避ける」規則。ClearAllergyでは高速な局所確認と、変更内容に応じた全体ビルドを併用する。ビルドを禁止する理由にはならない。
- ビルド専用の多数のSubagent、Xcode用CLI、全機能のRules分割。探索やログ量の問題が実測されてから検討する。
- 600 tokensを普遍的な上限にはしない。記事の事例値であり、内容の有用性を優先する。

**費用と判断**：今やる。入口の重複整理と5〜8種類の作業索引作成で約1〜2時間を見込む。維持費はディレクトリ責務やコマンド変更時の追記。細かなSkills作成は後回し。

## 2. SmartHR：複数AIツールの入口を共通のルールへつなぐ

**一次資料**：[マルチAIエージェント時代のルールの一元管理](https://tech.smarthr.jp/entry/2026/03/12/134348)（2026-03-12、新規事業開発チーム、murano）。

**確認できた実践**：同チームはツール別ルールの分散を解消するためAGENTS.mdへ集約し、CLAUDE.mdをシンボリックリンクとした。粒度調整が必要だったこと、簡単な構成では集中管理が合うこと、改善感は定性的で生成精度向上を保証しないことも明記している。全社規則でも、ツール間の読み込み仕様が完全に同じという証明でもない。[本文](https://tech.smarthr.jp/entry/2026/03/12/134348)

**ClearAllergyで採る機構**

- 既存AGENTSを入口の正本にする。`rules` の本文をAGENTSや別ツールの設定へコピーするのではなく、必要な章へ案内する。
- Claude Code等を実際に併用している場合だけ、対応する入口を追加する。シンボリックリンク、参照用の薄いファイルのいずれにするかは利用OS・ツールで読み込みを確認して決める。
- ルートAGENTSから文書にリンクしただけでは、すべてが常に読み込まれるとは仮定しない。対象タスクを与え、必要文書と適用規則を説明できるかを確認する。
- サブディレクトリAGENTSは「ここだけに適用される規則が複数あり、繰り返し見落とされる」場合に限る。まずは既存ファイルの適用範囲を明記する。

**人間向けとの整合**：同チームの別記事では、営業が読むPRDをNotion、技術設計をGitHubのdocsに置いている。これは読者に合わせた配置であり、すべてをGitHubへ統合すべきという事例ではない。ClearAllergyに同じ職種構成・読者事情がなければ、この二系統化は増やさない。[開発プロセスの記事](https://tech.smarthr.jp/entry/2026/06/09/102216)（初出2026-06-09、ページに2026-09-28の日付も表示）。

**移さない機構**：すべての階層へのAGENTS設置、未利用ツール向け設定、ルール数の増加自体を成果とする運用。単純な規約を毎回プロンプトへ追加するより、formatter/lintで表現できないかを先に判断する。

**費用と判断**：正本整理は今やる。約30〜60分と利用ツールでの確認。ネスト増設とツール追加は必要時。担当は変更PRの作成者が更新し、マージする人が適用範囲と矛盾を確認する。小規模なら専任の文書管理者を置かない。

## 3. CyberAgent / Ameba Spindle：AI向け文書と、安定した自動チェックを一緒に整える

**一次資料**：[Spindle 2025: AI エージェント × デザインシステムで変わる Web 開発](https://developers.cyberagent.co.jp/blog/archives/60944/)（2025-12-26、Ameba Spindleテックリード、原）。

**確認できた実践**：SpindleではAGENTS/CLAUDE、レビュー規則、反復作業の手順、探索しやすいディレクトリの一貫性を整え、古いテスト設定等も見直した。文書整備と実行可能なチェックを同じ開発サイクルの改善として扱っている。2025年の一プロダクトの振り返りであり、紹介された改善数値は複数施策が混在する前後比較である。[本文](https://developers.cyberagent.co.jp/blog/archives/60944/)

**公開実物での補強**：[SpindleのAGENTS.md](https://github.com/openameba/spindle/blob/main/AGENTS.md)にはセットアップ、レビュー、変更記録などの別ファイルへの参照がある。mainブランチは可変で、今回閲覧した内容を2025年当時の状態と同一視しない。

**ClearAllergyで採る機構**

- ルールを「読めば分かる説明」「機械で検証する制約」「人間が判断する事項」に分ける。
- `verification` は利用可能なコマンド・前提・検証範囲の入口にする。実在するlint、型チェック、テスト、buildを確認してから記載する。
- 実行記録には対象commit、コマンド、結果、未実施と理由を残す。「AIが確認した」だけで完了にしない。
- 例えばAPI契約変更なら、入力の正常・異常系、認可境界、消費側への影響を確認項目にする。UI変更なら表示だけでなく入力・エラー・空状態を対象にする。具体的な必要範囲は既存実装と変更内容で絞る。
- ドキュメント内のローカルリンク、存在しない参照パス、重複した命令の検出は小さな決定的チェックの候補にする。

**移さない機構**：Spindle固有のMCPサーバー、デザインシステム運営体制、リリース自動化一式。「AI導入で何倍」という数字をClearAllergyの見積りへ転用すること。構造を整える名目でapp/features/components/libを一斉移動すること。

**費用と判断**：今やるのは既存チェックの棚卸しと文書への対応付けで約1〜2時間。実行基盤が既にあるなら文書参照チェックはさらに1〜2時間程度。テストの新設や不安定テスト修復は別タスクとし、最重要の変更経路から着手する。

## 4. リクルート / Knile：今の仕様と、そう決めた理由の履歴を分ける

**一次資料**：[データ基盤 Knile のプロダクトマネジメントの取り組み](https://techblog.recruit.co.jp/article-5157/)（2022-03-08、多田雅斗、Knileチーム）。

**確認できた実践**：KnileはADR、Spec、利用者Docs、障害対応記録を区別。Specは最新の設計、ADRは判断時点の経緯を保存する。約70リポジトリを跨ぐ仕様の置き場が必要だった点が重要で、4つの文書リポジトリを作ること自体が目的ではない。AI以前の知識管理事例として参照する。[本文](https://techblog.recruit.co.jp/article-5157/)

**ClearAllergyで採る機構**

- `guide` と `rules` は今有効な説明・制約。`research` は選択肢や根拠。`verification` 内の実行記録はその時点の証拠、と役割を定義する。
- 調査で採用された決定は、現行のguide/rulesへ反映する。調査文書にだけ新しい規則を埋め込まない。
- 判断履歴を残す必要があるときだけ短いADRを作る。内容は「背景／選択肢／決定／受け入れた不利益／見直す条件／関連PR」で足りる。
- 既存researchに判断を記録する方法があれば、その型を先に再利用する。新しいdecisionsディレクトリは、複数の判断履歴が埋もれて検索できない場合に検討する。
- 対象例は認証境界、API契約、データ整合性、外部連携、あとから戻しにくいライブラリ選定。変数名や一時的なUI調整ごとには作らない。

**移さない機構**：4リポジトリへの分割、Sphinx等の文書サイト導入、すべての実装に重い設計書、後から推測して埋める大量の過去ADR。

**費用と判断**：現状・履歴の区別は今やる。既存文書の分類と見出し調整に約30〜60分。ADRの追加は重要な選択が発生したときに1件15〜30分程度。全面移行は見送る。

## 5. DeNA / Ledge：知識の量より、欠落・参照不能・鮮度を直す

**一次資料**：[社内AIヘルプデスク「精度80%の壁」を突破―ナレッジ管理ツール開発の意思決定](https://engineering.dena.com/blog/2026/04/ai-helpdesk-knowledge-ledge/)（2026-04-23、IT戦略部、Yuko Morishima）。

**確認できた実践**：Ledgeは回答できなかった問い合わせから更新案を作り、リンク切れと長期未更新を検出する。AIの案を直接正本へ上書きせず、人間が採否と反映を判断する。記事は社内ヘルプデスクのナレッジ改善であり、コードリポジトリや全社開発標準の事例ではない。[本文](https://engineering.dena.com/blog/2026/04/ai-helpdesk-knowledge-ledge/)

**ClearAllergyで採る機構**

- AIが毎回迷う箇所や、レビューで繰り返された誤解を、対応PRに「どの文書の何を直すか」の差分として添える。
- 新規文書を増やす前に、既存文書の追記で足りるか、リンクが辿れるか、現行コードと矛盾していないかを確認する。
- `research` と検証記録には対象時点・状態を明示する。古い文書は単に日付が古いという理由で誤りにせず、現行の判断に使えるかを確認する。
- 当面はPRの短いチェック項目で運用する。「公開契約・手順・配置・制約が変わる場合、対応文書を更新。不要なら理由を1行」。文書管理専用サービスは作らない。
- 文書更新者はその変更の担当者。AIによる提案は人間が確認し、コードと同じ差分レビューに載せる。

**移さない機構**：日次RAG分析、専用Wiki管理アプリ、全ページへの期限設定、自動上書き。ヘルプデスクの回答精度改善をコーディング精度の効果として引用しない。

**費用と判断**：今やるのはPR確認項目と更新責任の明文化で約30分。実際の更新は影響があるPRで数分。長期未更新アラート等は、情報量が増え、見落としを確認してから。

## ClearAllergyの既存構成への最小対応案

以下は新しいフォルダ体系ではなく、既存文書に持たせる責務案。実際のファイル名・リンクは現行リポジトリに合わせる。

| 置き場 | 答える質問 | 含めるもの | 増やさないもの |
|---|---|---|---|
| AGENTS.md | 作業前に何を守り、どこへ進む？ | 重要制約、作業別入口、完了条件へのリンク | 全仕様、一般的な開発教科書、長い調査履歴 |
| guide | このアプリはどう動き、どう開発する？ | 現行の全体像、セットアップ、主要境界 | 別文書にある詳細ルールのコピー |
| rules | この変更で必ず守ることは？ | 適用範囲、理由、必要なら短い例、強制手段 | あらゆる例外を常駐させる巨大ルール集 |
| change-map | この要求を変えるとき最初に何を見る？ | 実在コードへの入口、関連箇所、対応する検証 | 全ファイルの手書きカタログ |
| research | なぜこの案を検討し、何を採用した？ | 日付、対象、出典、結論の状態、採用先へのリンク | 現行ルールの唯一の保管場所 |
| verification | 何を確認し、どこまで分かった？ | 再利用する手順と、commit付きの実行記録の区別 | 昔のPASSを現在の品質保証として扱うこと |

### change-mapの作り方

最初は次の5行程度で十分。正確なHonoの配置や機能名を監査したうえで実在パスへ置換する。

| 変更の意図 | 最初に確認する場所 | 追加確認 | 検証観点 |
|---|---|---|---|
| 画面・導線 | appの対象ルートと関連features | Server/Client境界、loading/error、利用API | 主要操作、空状態、エラー状態、関連型 |
| 業務機能 | 対象featuresの既存実装 | 呼び出し元・呼び出し先、共通化の必要性 | 仕様の正常系・境界値・異常系 |
| API契約 | Honoの実際のルート定義 | 入力検証、認可、利用側 | 返却契約、認証・認可失敗、入力不正 |
| 共通UI | componentsの既存パターン | 対象機能だけのUIを共通化していないか | 利用箇所の表示・操作・アクセシビリティ |
| データ | prismaのschema・migrationと利用コード | 既存データ、生成物、トランザクション境界 | schema整合、migrationの影響、関連API |

これは新しい依存ルールを勝手に導入する表ではない。`lib` の実際の用途やHonoのルート配置は、現在のコードから確認する。ファイルを移動しなくても「どこを起点に、何を辿るか」を明らかにできる。

## 今／後で／見送る

### 今：1つの小さな文書整理PR

1. AGENTSと5種類の文書の重複・矛盾を棚卸しする。
2. 一つの規則につき正本を決め、残りを参照へ置き換える。
3. change-mapを主要な変更種類に絞り、実在コードと検証へつなぐ。
4. 実際のpackage scripts・CIとverificationを突合する。
5. 「仕様・境界・手順を変えた担当者が文書も更新する」をレビュー条件にする。
6. 新規セッションのAIと人間が、代表的な3タスクの変更入口・適用規則・検証範囲を説明できるか確認する。

初回の目安は半日〜1日（約4〜8時間、文書量・矛盾量による）。コード移動、テスト基盤新設、データ移行、運用システム開発は含めない。

### 後で：実際の不便が残るものだけ

- ローカルリンク・参照パスのCIチェック。
- 繰り返し違反される重要制約をlint・テストへ移す。
- 独立した規則が十分に増えた領域にだけ子AGENTSを置く。
- 重要な決定の履歴が散らばったときにADR索引を設ける。
- 何度も同じ手順を失敗するときに限り、手順をスクリプトや小さなSkillへまとめる。

### 見送る

- 企業事例に合わせた大規模フォルダ再編、Clean Architectureの全層導入、用途がないrepository/use-case層。
- 既存のdocsを捨てる全面移行、複数の正本、未使用AIツールの設定追加。
- すべての変更のADR化、全ドキュメントの常時読み込み、コンテキスト量の固定数値目標。
- 独自RAG・MCP・文書ポータル、AIの判断だけによる文書の自動上書き。

## 成功の確かめ方

「文書が増えた」「AIの出力が長くなった」ではなく、次を比較する。

- 同じ代表タスクで、作業前に読むファイルと最初の編集候補が絞れるか。
- 人間とAIが参照する規則が一致し、異なる文書から逆の結論にならないか。
- 存在しないパス・古いコマンドがなくなったか。
- 変更後に実施した確認と、未実施・失敗を区別して報告できるか。
- レビューで指摘した誤解が、その場限りの会話で終わらず、正しい文書か自動チェックへ反映されるか。

最初の3つ程度の実作業で試し、不要な説明は削る。これは効果観測の初回サンプルであり、「3件で十分な品質保証ができる」という意味ではない。

## 調査対象の選別と追加資料

- LINEヤフー、CyberAgent、リクルート、SmartHR、DeNAの上記5事例を採用した。SmartHRはメガベンチャーという分類より、小規模な新規事業チームに近い条件を優先した。
- メルカリの公式アカウントによる [DevDojo: Mercari Design Doc 2024](https://speakerdeck.com/mercari/devdojo-mercari-design-doc-2024)（公開2024-05-30、資料内はApril 2024）も確認した。設計判断を共有する教育資料として有用だが、ClearAllergyの小規模整理ではKnileの「現状と履歴の区別」と機能が重なるため、主な事例数を増やさなかった。全社の全変更にDesign Docが必須という根拠にはしない。
- LINEの2026年2月登壇・3月イベント報告に出る「約150行」と、今回採用した1月記事の「約600 tokens」は別時点の記述。数字を混同しない。
- 公開記事の企業名は採用理由にならない。今回の選別基準は、同じ失敗を減らす仕組みが読み取れること、既存構成へ小さく移せること、維持する人と確認方法を具体化できること。
