## 観察と保証の候補

R01: 現在は架空店舗・架空メニューを用いるUI検証用プロトタイプ。READMEと `lib/public-prototype.ts` は実際の飲食判断への使用を禁止する。依頼の「飲食店が登録し利用者が確認するWeb Application」は機能の説明として合うが、実運用済みと解釈すると矛盾する。本番データが架空のみであることは未確認。

Productが保証を目指せる対象は、登録内容の意味を保った保存・公開、対象店舗の識別、入力の欠落を否定情報へ変換しないこと、権限・更新の整合性、保証範囲の説明。厨房の実態、仕入れ情報の真実性、交差接触の不存在、個人の摂取可否、あらゆる原因食物の網羅、緊急対応・診断は保証対象にしない。これらは一般的な免責文で代替できる設計課題ではない。

実店舗利用を開始する判断は HD-01。将来の研究要件と現行prototypeの受け入れ条件を混ぜない。サービス提供時の法的責任は本調査で判定しない。

## Stakeholdersと境界

| Actor | 提供/制御するもの | 失敗の影響・未確認 |
| --- | --- | --- |
| 当事者 | 確認品目、閲覧、店舗への質問 | FREEの誤解、選択漏れ、表示範囲外の原因食物 |
| 保護者・代理判断者 | 他者のための情報確認 | 複数人の設定取り違え。診療情報は収集しない |
| 同伴者 | 情報共有・注文の伝達 | スクリーンショットやQR先の時間差、本人の意向との不一致 |
| 店舗スタッフ | 原材料と当日の変更の把握 | UIを正しく入力しても仕入れ・調理実態が異なる |
| 店舗所有者 | 登録・公開・非公開 | 1 owner/1 shopモデル。複数スタッフ権限はない |
| 運営管理者 | 招待・障害対応 | 店舗編集権限を自動的には持たない。緊急停止の責任者は未決 |
| 開発・保守担当 | code/migration/CI/config | DB直接書込・migrationがAPIを迂回する |
| Clerk / DB / Blob / Vercel | identity/storage/配信 | outage・設定差・外部結果不明。CAの食品判断はしない |
| 仕入先・調理担当 | CA外で原材料・工程を変更 | システムに変更通知が届かない経路 |
| 支援技術利用者 | keyboard/screen reader等 | 正しいDOMと実理解の両方を検証する必要 |

## 責任分担の提案（E7）

店舗は登録根拠・変更の通知を担い、CAは情報処理と限界の明示を担う。運営は誤情報の受付・封じ込め・履歴確認の経路を用意する。利用者への確認依頼だけに依存しない（X01/X02/X05）。役割分担の契約・運営体制・専門家レビューはHD-01/HD-04。

公開メニューを非公開にしても配信済み画面・画像・印刷物を回収できない。QRは店舗URLへの参照であり、食品や提供日を証明しない。
