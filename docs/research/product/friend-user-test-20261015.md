# 友人に協力してもらう操作・理解テストの準備

作成日：2026-10-15。状態：**手順と空記録票の草案。友人への連絡、同意取得、参加者との実施、結果の記入は行っていない。**

[調査・検証方針](research-and-friend-testing-policy-20261015.md)に沿って、既存の架空料理を使う小さな確認を準備する。実店舗へ接触せず、店舗側の仕事は公開資料・事例・シナリオで精査する。友人には画面の操作と読み取りへの協力を依頼する方向であり、店舗の実務調査や食品の安全性評価を任せる計画ではない。

この文書は進行役用。操作者へ台本・期待結果・全資料をまとめて配らない。[友人テスト用の空記録票](friend-user-test-record-sheet-20261015.md)と一緒に使う。実試験の開始と連絡は別作業であり、この準備だけで実施を開始した扱いにしない。

## 何を確かめるか

既存画面について、友人が情報を見つけられるか、表示から肯定できる事実と分からないことを区別できるか、操作後の保存・公開状態を説明できるかを観察する。分からないと答えたこと自体を失敗にしない。対象はその人、その画面、その資料、その順序での操作と回答である。

少人数の友人の回答から、食品の安全性、事故低減、市場需要、実店舗の負担、支払意思、患者全体の理解度を結論づけない。友人関係による遠慮、協力者の偏り、課題の学習も記録する。人数と協力者は実施前に決め、当事者であることや病歴の説明を参加条件にしない。

友人が「店員役」をする場合も、架空資料を使う操作の確認に限る。仕入先との実際の照合、繁忙時の運用、店舗担当者の知識や責任を再現したことにはならない。実食、診断、健康歴、実店舗の資料・連絡先を集める必要はない。

## 実施前に固定するもの

以下を実施担当が埋め、第三者が見ても何を提示してどう分類するか確認できる状態にする。未確定の欄が残る間は準備段階とする。

1. 対象者と役割、同意の説明、任意中止と削除の方法、実施担当、観察する条件と順序を決める。リリースの受入閾値はこの少人数テストで代決しない。
2. 使用コードのcommit SHA（ソースの版）、fixtureのファイルhash、CSS・架空資料・判定表の版、画面幅、ブラウザを記録する。過去のSHAを今回使った版として転記しない。本書の作成ではfixtureを再実行していない。
3. 進行役だけが使う判定表を条件ごとに作る。条件ID、実際に見せる画面・資料、肯定できる事実、不明な事項、見せない情報、標準質問、援助の順序を先に固定する。起動後に実際の表示を照合し、想定と違えば質問や正解を後付けせず、その条件を保留する。
4. 操作者用の画面には割り当てた資料だけを出す。全資料、現物相当台帳、採点票、検証JSON、進行役URLとtoken（制御用の秘密の文字列）は渡さない。進行役の台帳は別PCまたは進行役だけの紙で管理し、PC・ブラウザ履歴・ターミナルを操作者と共用しない。
5. 条件設定は開始前に済ませ、観察中に操作者端末で進行役画面を開いて返さない。既存スクリプトは別PCから接続する機能を持たないため、端末・資料授受・条件切替の方法を事前に整える。分離できなければ開発者の予行までに留める。
6. 非公開の記録先、アクセスできる担当者、具体的な削除日を合意する。録音・録画を使わず、匿名の手記で進める。これらを確認してから、別作業として実施に移る。

同じ人が利用者役と店員役をするなら、台帳や完全資料を見る前に利用者役を先に行う。その後の回答を同条件の初見回答へ数えない。利用者役は少数の条件を選び、S0と見た目が同じS5を同じ人へ続けて出して隠し変更を推測させる構成を避ける。

## 当日の説明と問いかけ

開始時に、次の説明をする。実施日・保持/削除日等は合意済みの具体値を使う。

> 架空の店と料理の画面を使い、操作と説明の分かりやすさを確かめます。あなたの能力や実際の食事を評価するものではありません。病歴や食事の経験を話す必要はありません。答えたくない問いは飛ばせて、いつでもやめられます。協力を断っても不利益はありません。録音・録画はせず、匿名のメモを取り、合意した日までに削除します。記録や回答を公開しません。分からないことは分からないと答えてください。

同意を得た事実と説明の版だけを空票に記録し、氏名や連絡先をこの票へ入れない。実施中に健康・被害の相談へ移った場合は、その詳細を転記せず課題を止める。

### 1. 初見の自由回答

利用者役には選んだ条件の画面だけを提示し、「この画面を自由に確認してください。何が分かると思ったか、気になったことを教えてください」と尋ねる。登録値の意味、隠れた変更、台帳の答えを先に説明しない。沈黙を急いで埋めず、回答・探した箇所・迷いを記録してから次へ進む。

店員役には割り当てた仕事資料と作業依頼を提示する。例は「この資料で分かる変更を記録し、次に必要だと思う操作を行ってください」。最初から公開停止や特定状態の入力を正解として読み上げない。S1等を事前設定した回は、その状態から操作したと記録し、変更の発見力を測ったことにしない。

### 2. 標準質問

自由回答を確定してから、該当する質問を同じ言い方・順序で行う。この段階の回答は、自由回答に出なかった気付きとして別に残す。

1. 「この表示は、どの料理の、どの情報を示していますか」
2. 「この情報から言えることと、まだ分からないことは何ですか」
3. 「そう考えた根拠は、画面や資料のどこにありますか」
4. 日時が表示される条件では「この日時は何の時点だと思いますか」。表示がない条件で日時を推測させない。
5. 「さらに確認したいことがあるなら、何をどう確かめますか」。実店舗へ連絡させず、意図の回答として記録する。
6. 操作をした条件では「いま何が保存され、何が公開され、何が未確認ですか」。合成保存の結果を実DBの永続化と扱わない。

未申告条件で「何が変わりましたか」と尋ねたり、停止画面で「乳を使ったから止まりましたか」と誘導したりしない。画面にない情報を答えられないことは、画面の限界として記録する。

### 3. 援助後

標準質問までを確定してから、必要な場合だけ、事前に決めた援助を一つずつ行う。「同じ画面内の場所を案内」「同じ資料の読み方を案内」「追加の仕事資料を渡す」「意味を説明する」を区別し、時点と実際の文言を記録する。追加資料後は、回答者が知り得る範囲が変わった新しい段階である。

B-?やS5の初回回答後に完全B-1を渡した場合、その後の乳使用の回答を初回の正答へ上書きしない。採点票・進行役画面・履歴が先に見えた回は、見えた時点までを記録し、以後を未提示条件の初見回答へ数えない。

終了時は「架空の登録と分からないことの読み取りを確認しました。現物、未申告変更、厨房、将来の提供や食べられるかを確かめたものではありません」と説明し、任意の負担感・迷い・改善してほしい一項目を聞く。

## 時間・記録・削除の案

時間を測る場合は、情報探索、操作、標準質問、援助後を分ける。待ち・中断・模擬待機も区別する。記録するのはその架空課題の操作観察時間であり、実店舗の初期登録・更新工数ではない。未実施を0分で埋めず、比較対象と順序を固定していない回から短縮率を出さない。

匿名IDは外部IDと結び付けない。削除依頼に使うセッションIDを協力者にも渡す。録音・録画は既定で行わず、回答の手記も必要最小限とし、混ざった氏名・連絡先・健康情報は記録対象から除く。架空の表示画像と回答メモを区別し、個人情報のある画面を保存しない。

保存先は、実施前に決めたアクセスを限定できる非公開のローカル場所とする。回答や記入済み票をリポジトリ、GitHub、共有リンク、公開資料へ載せない。案として、生メモは実施後14日以内、個人に結び付かない改善メモも実施後30日以内に削除する。**実施前に実施日から具体的な削除日と担当を決めて合意し、空票の欄を埋める。** 未合意のままこの日数を実施済みの方針にしない。途中辞退・削除依頼の扱いも同じ説明で確認する。

## 結果を受け取るときの判断

空票は実施まで空欄のままにする。実施した場合も、役割・条件・提示順・表示版・自由回答/標準質問/援助後を分け、実施人数と課題数を混ぜない。未完了・中止・判定不能を分母から落とさず、重大誤認0件を安全性や実店舗効果の証明にしない。

可能なら初回回答を2人が独立に分類し、不一致と解決理由を記録する。できなければ未実施と残す。見つけた混同、情報の不達、操作の詰まりから次に直す一項目を選び、既存の手順で解消できるかを先に検討する。機能追加、実店舗調査、将来UIの採用、一般公開の判断はこの準備・少人数の観察から自動で決めない。
