# 食品確認フォームを外し、保存と公開を分ける判断

2026-10-21 UTC。基準main `d1e155b30d6cc2034ac2a007a59623e1b213303a`。ユーザー承認に基づく実装判断。本番未適用。

## 判断と理由

ユーザーは長い食品確認フォームを不要とし、新規・食品変更を非公開で保存してから、保存済み内容を見直して別に公開する方針の実装とテストを承認した。「何でかは書いてね」という依頼により、理由と境界をここに残す。

根拠・範囲・日時を自由記述で必須入力しても、資料や現物をアプリが取得・検証するわけではない。形式的な記入負担に対し、確認品質をどれだけ改善するかは未検証であり、長文フォームの維持を品質の証明にしない。今回の判断は、記入負担が実店舗で定量的に減った、誤表示や事故が減ったという実証ではない。

食品変更後の古い確認の流用は、長文入力欄の存在とは分けて防ぐ。食品内容の版と公開操作をDB内で結び付け、食品・品目・マスタの変更で公開の版対応を失効させる。UNKNOWNや欠損をFREEへ変換せず、所有権・Origin・保存版の競合拒否・未解決事項の制約を維持する。

公開操作は、その保存済み内容を店舗担当者が公開する操作である。原資料や食品を照合したこと、安全性、摂取可否、厨房の交差接触を保証する記録として扱わない。食品根拠や原資料確認日時を自動生成しない。

## 採用した操作

1. 新規作成・食品変更は非公開で保存する。文字が同じ仕入れ仕様・代替使用・工程の変更申告も残す。
2. 未保存変更を保存し、保存済み内容を見直した後、別の「公開する」を操作する。
3. サーバーは所有店舗と保存版を再確認し、現行の食品版・全品目・未解決状態を同じトランザクションで照合する。
4. 価格や画像構図だけの変更は、既存の公開状態を維持する。公開停止は食品確認フォームに依存させない。

従来の「食品変更と新しい食品確認記録を同時保存して公開する」操作からの変更である。画面の非表示だけではAPIとDBの記録必須条件を満たせないため、公開操作の状態管理と新migrationを併せて変更する。

## 履歴と移行

`MenuFoodReview`の既存根拠・範囲・確認日時・未解決事項・食品snapshotは書き換えず保持し、編集画面から読み取れる。新しい公開操作は`MenuPublicationConfirmation`へ記録し、記録時刻はその公開操作の実際の記録時刻であり、原資料を確認した時刻ではない。

移行時は、既に公開中で実在する現行食品確認記録があるものだけ、既存公開の版対応を維持する。その記録IDを移行由来として分け、新しい人の公開操作を捏造しない。下書き・未解決・旧版を自動公開しない。移行後の食品変更で移行由来の対応も失効し、旧記録を再利用しない。

旧`foodReview`入力と新規作成時の公開要求は400で明示拒否する。既存の非公開保存・価格変更・公開停止は維持する。古い画面は再読み込みして新しい公開操作へ進む。旧migrationは変更しない。本番への適用・merge・deployは今回の承認対象外である。

## 未解決事項の明示解除（ユーザー暫定承認）

親タスクが2026-10-22 01:28 JSTに提案し、例を使って「以前の未解決内容を表示→実際に確認・対応した店舗担当者がこの内容は解消した→別に公開」と説明した。その後ユーザーが「運とりあえず」と暫定承認した。全メニューへの長文フォーム再導入や、押すとFREEへ変わる仕様ではない。CAの仕様への承認であり、merge・本番DB・本番反映の承認ではない。

最新の未解決記録と保存済み食品版を対象とし、店舗担当者が明示解除する。`MenuFoodIssueResolution` へ元記録ID・対象食品版・実操作者・実操作日時・元の未解決本文を追記する。旧 `MenuFoodReview` は更新・削除しない。食品資料やその確認日時を生成しない。解除の日時はこの操作の実際の記録時刻であり、食品安全の保証ではない。

解除だけでは非公開のまま、通常保存や公開で自動解除しない。解除と内容編集・公開を同じpayloadに混ぜない。別の「公開する」で、所有権・Origin・CAS409・現行食品版・UNKNOWN/入力条件・最新未解決とその解除を再確認する。食品版や最新未解決が変われば古い解除を流用しない。価格だけの変更では食品版と解除の対応を維持する。

新しいmigration `20261021010000_food_issue_resolution` は解除履歴を空で追加し、旧未解決を補完解除しない。履歴UPDATEを拒否し、DELETE/TRUNCATEでは公開対応を失効させる。UIは未解決があるメニューだけに解除操作を出し、履歴では当時の未解決原文と各記録の最新解除の食品版・操作日時を表示する。全解除履歴と操作者はDBに保持する。運営限定フローや追加の自由記述は採用しない。

## コンテキストを維持する既存の導線

CAには、後続作業が仕様と根拠を辿るための次の構造がある。全てを本人が執筆したことや、全員が毎回利用していることを意味しない。

| 役割 | 既存の入口 |
| --- | --- |
| 作業ルール・開始確認・必須検証 | [AGENTS.md](../../../AGENTS.md) |
| 最初に読む順序 | [README](../../../README.md#reading-order) |
| 状態・公開・権限の仕様正本 | [共通ルール](../../guide/rules.md) |
| 変更から仕様・実装・テストへ辿る | [変更対応表](../../guide/change-map.md) |
| 文書更新先・時点・完了条件 | [文書保守](../../guide/maintenance.md#update-map) |
| 判断・調査・原稿・適用限界 | [研究索引](../README.md)、[主張と根拠](../04-claim-register.md) |
| 実行結果・未確認と過去記録 | [検証の入口](../../guide/verification.md)、`docs/verification/` |

これは「仕様を文書へ置く」だけでなく、変更時に関係する文書・実装・テストへ到達するためのコンテキスト整備の実例である。今回も公開条件の正本、操作、内部処理、変更対応表、検証記録を同じ変更で揃える。
