## 目的と今回できること

架空の一料理で、材料変更の発見、対象の特定、記録、公開停止、根拠の確認、再公開、利用者側での読み取りを順に辿る。店の作業が別工程へ移る箇所と、画面から分からないことを利用者がどう解釈するかを後で観察できるようにする。食品の摂取・医療判断・実店舗運用は扱わない。

今回の準備は台本、匿名記録票、隔離画面の必要条件の設計であり、募集、連絡、同意取得、被験者の操作観察、健康情報の収集は行っていない。開発者による架空ケースの予行と、参加者が同意して行う理解度観察は別記録にする。

先行するアプリ修正は別の成果である。

- #73: 店舗基本情報の古い全量フォームによる上書き、DB確定後の公開反映失敗、不正200の成功扱いを技術的に修正・回帰検証する。一料理の演習だけで、この3系統の検証を代替しない。

## 進行役資料と初回回答の分離

この台本・期待結果・全資料・検証JSONの現物相当台帳は**進行役用**であり、操作者の読み物としてまとめて配らない。操作者の通常navには進行役の入口を出さず、`/materials` と通常state DTOには条件に割り当てた資料だけを返す。

| 条件 | 操作者へ渡す仕事資料 | 初回回答前に渡さないもの |
| --- | --- | --- |
| A確認済み・通常STOP・確認記録なし | A-1 / R1 | B完全版・採点期待結果 |
| 変更申告後・B確認済み | B-1 / R2 | 未申告の台帳・他条件の期待結果 |
| B-? / 複合材料不明 | B-?受領メモのみ | 完全B-1、飾りの抜けという解答、全資料索引 |
| 旧新併存・未解決 | A-1、B-1、F-03の対応不明という仕事資料 | 公開判断の正解や採点結果 |
| 未申告 | アプリにあるA-1 / R1 | 現物相当B、未申告台帳、検知不能という解答 |

進行役画面・全資料・条件/故障制御には起動時だけ出力するランダムtokenが必要。単に `?facilitator=1` を付けた直接URLや、tokenなしの制御要求は拒否する。ただしこれはloopback演習内の表示・制御の分離であり、公開アプリの認可、同じPCのOS・履歴・開発者ツールからの機密保護を保証する仕組みではない。

開発者の予行では一人で両面を確認してよい。その回を初回の理解度データにしない。自発回答を観察する際は、進行役の採点票/完全資料を別PCまたは進行役だけの紙で管理し、操作者と進行役で同じPC・ブラウザ履歴・ターミナルを共有しない。操作者へtokenや進行役URLを配らず、条件設定は開始前に行う。観察中に操作者の端末で進行役を開いてから端末を戻す運用はしない。このscriptは別PCからloopbackへ接続する機能を持たないため、参加者実施に必要な端末・事前設定・資料授受は別に整える。

条件を変える・追加資料を渡すときは、初回回答の記録を確定し、何をいつ提示したかを記録票に残す。B-?や未申告の回に完全B-1を渡した後の回答は「追加資料/補助後」であり、初回の自発回答へ上書きしない。進行役面や全資料を先に見た場合も別扱いにする。

## 演習の単位と架空の真値

変更対象は一料理「架空・きのこの小丼」、変更材料は一つの複合ソースとする。架空店舗「演習店 F」においてソースAをBへ切り替える。実在製品・店・仕入先の事実を表さない。材料を自動解析して状態を推定せず、資料カードに独立して定めた架空の真値と入力値を照合する。

| 資料 | 内容 | 観察上の扱い |
| --- | --- | --- |
| レシピ R1 | 米、きのこ、ソースA、白ごまの飾り | 主材料だけでなく、ソースの内訳と飾りまで対象にする |
| ソースA / A-1 | 架空資料に小麦・大豆の使用を明記。乳はこの資料・レシピ範囲では原材料に使用しないと明記 | 「乳がラベルに見当たらない」から非使用を推定しない |
| ソースB / B-1 | Aと同じ小麦・大豆に加え、乳を使う架空仕様 | 乳の状態が変わる。その他を未知からFREEへ一括変換しない |
| レシピ R2 | ソースだけをBへ切替。他の構成はR1と同じ | Bの採用予定日と、実使用の開始を別にする |
| B不完全版 / B-? | 製品名だけ分かり、複合材料の内訳・版の対応を確認できない | B-1を持っている場合と同じ確認済み扱いにしない |
| 在庫 O/N | 旧ソースAの仕込みと新ソースBが併存。提供分との対応が取れる場合と取れない場合を分ける | 新しい資料の入手だけで、すべての提供分をBに一括変更しない |
| 工程カード K-? | 共用器具・交差接触について今回の資料では確認していない | 乳FREEから厨房全体で乳を使わない、交差接触しない、摂取可を導かない |

マスター上の全品目は、fixtureの架空状態表で明示する。架空資料でFREEと指定した項目も、実物の非使用や安全の証拠ではない。実際のアレルゲン・材料の対応を推定する仕組みは追加しない。マスター件数を固定した入力UIは作らない。

## 始める前の確認

開発者だけの予行では、画面の存在、状態切替、記録票の不足を確認する。これは人の理解度・店舗工数の測定ではない。

参加者を伴う実施に移る前に、人間が対象者、同意の説明、実施担当、記録へのアクセス、保持・削除方針、採点案、重大誤認時の対応を確定する。これらの未決定は準備作業を止める理由にはしないが、参加者実施を始めた扱いにはしない。既存 #39 / #52 の条件を本草案だけで解除しない。

実施の冒頭では、以下だけを共通説明する。途中で正解を教える場合は、その時点からの結果を「補助後」として分ける。

> これは架空の店と料理を使う操作の確認です。実際の飲食判断や、ご自身の病歴・食事の経験をお話しいただく必要はありません。分からない場合は分からないと答えてください。操作できない、答えたくない、途中でやめたい場合は、そのまま伝えてください。画面や手順の分かりにくさを調べます。

## 基本の進行台本

所要時間は未測定であり、目標分数を正解や成功条件にしない。初回は全項目を店舗の初期設定として要求せず、基本経路と分岐を別セッションとして扱ってよい。

| 段階 | 進行役が提示するもの・質問 | 観察して記録するもの | 補助前の期待結果・限界 |
| --- | --- | --- | --- |
| 0. 版を固定 | R1/A-1と公開済み画面を提示。「この料理について、今の表示から分かることと分からないことを説明してください」 | 自発回答、根拠の表示、探した箇所、初期設定 | 乳の原材料非使用と工程未確認の区別。自分が食べられるかは尋ねない |
| 1. 変更を知る | 「本日、Aの代わりにBを使うことになりました」。B-1と、まだ使っていない／既に使い始めた、いずれかの提供記録を提示 | どの料理・構成・期間を確認したか、開始の推測、資料取得待ち | 予定と実使用を分ける。アプリが現物の切替を自動検知した扱いにしない |
| 2. 対象を見つける | 「更新が必要な料理を一覧から見つけ、どの確認が必要か説明してください」 | 一覧の状態・件数・理由・編集への到達、見落とし、探索時間 | #74の再確認待ちを見つける。通常STOP行を再確認失効と混同しない。状態を変更前に自動で出すと検知能力を過大評価するので、変更申告後の一覧とする |
| 3. 変更を入力 | 「この提供内容を現時点で分かる範囲で反映してください」 | 原材料欄だけか、乳状態も見直したか、未解決の書き方、確認資料・範囲、入力やり直し | 原材料・状態・根拠の整合を見る。食品変更の保存後、旧食品確認のまま公開しない。未確認はUNKNOWN/未解決として残す |
| 4. 保存を確かめる | 「いま何が保存され、何が公開されているか説明してください」 | 成功/競合/反映未完了の区別、再送意図、未保存入力の保持、保存内容の確認方法 | シミュレーション応答と実DB永続化を分ける。店舗基本情報の #73 の実DB検証は別証拠 |
| 5. 再確認 | B-1/R2/対象提供分の情報が揃った条件を提示。「確認できた範囲を記録し、次の操作を選んでください」 | 根拠資料、製品/版、確認範囲、確認日時、未解決事項、公開判断 | 現行食品版へ記録。未解決のまま公開可能にしない。チェックを埋めた事実と、現物の照合を混ぜない |
| 6. 公開後を読む | 利用者役へ新しい画面を提示。「この料理と乳について何が分かり、何が分かりませんか。次に必要な確認はありますか」 | 初回の自発回答、選択品目、CONTAINS/MAY/FREEの取り違え、店への確認対象と意図 | 乳使用の見落とし、厨房保証への飛躍を分類する。質問だけで実際の確認行動を観察したことにしない |
| 7. 訂正/STOP | 「公開済みの情報に誤りが見つかりました。必要な操作を行い、利用者が旧URLから来たときどうなるか確認してください」 | STOP到達、未保存フォームを送らないか、再取得結果、訂正情報への到達と不達 | 通常STOPと食品確認失効を別に観察。現行not-foundが訂正説明を届ける機能とは言えない。既存タブは回収できる保証なし |
| 8. ふり返り | 「余分だった操作、足りなかった情報、迷った箇所を教えてください」 | 任意回答、補助の内容、負担移転、未完了理由 | 「簡単だった」という自己申告だけで時短・実運用成立を結論しない |

食品確認失効の一覧を表示する前に、変更を申告するという操作が必要である。最初から再確認バッジを付けたfixtureだけを使って「未申告の変更を発見できた」と評価しない。分岐B3では必ずこの違いを見せる。基本経路で現物相当をAからBへ切り替える段階は進行役が先に固定し、たとえば初回Aの読取り後に未申告条件へ切り替えてからB資料を追加提示する。フォームでBと入力したこと自体を、現物がBへ変わった証拠にはしない。

## 記録と時間の扱い

時間を記録する場合は、資料探し、提供分との照合、入力、確認記録、公開状態確認、訂正、問い合わせ準備の各工程に分ける。待ち時間、操作時間、中断時間は別々の欄に置く。fixtureが人工的に挿入する待ち時間は「模擬待機」と記し、仕入先の実応答待ちに加算しない。

参加者と実施した場合の操作時間も、架空ケース・その端末・その順序の観察値であり、実店舗の通常業務の所要時間ではない。紙や表計算との比較を行うなら、同じ対象範囲・資料品質・未解決の扱いで比較する。学習効果があるので順序、同じ課題を先に見たか、補助の有無を残す。比較しない回から「短縮率」は算出しない。

店舗の作業が減ったように見えても、仕入先回答、問い合わせ、印刷差替え、同僚への説明、利用者の確認断念へ移っていないかを記録する。行っていない工程を0分で埋めず、未実施とする。

## 採点案と次の判断

この採点は分類案であり、リリース判定・#39の閾値を確定しない。

- **区別できた**: 該当する登録・対象・版・不確かさを、自分の言葉で根拠とともに説明した。
- **混同した**: 登録されていない保証、対象/料理/版の取り違え、未知から非使用への変換が回答にある。
- **回答から判定不能**: 無回答、抽象的な回答、進行役の誘導で初回理解を評価できない。
- 操作結果は別に **完了 / 補助後完了 / 未完了 / 中止**。判定不能・中止・未完了を成功の分母から落とさない。

重大誤認の候補は、UNKNOWN→FREE、FREE→摂取可/交差接触なし、CONTAINS/MAYの見落とし、別料理/別版の合成、旧版を現行保証として扱う回答である。1件でも見つかれば原因・誘導・画面・課題を検討する材料にする。何件なら一般提供可という受入閾値は人間が別に決める。0件でも安全性や誤認防止を実証したことにはしない。

可能なら2人が初回回答を独立に分類し、不一致と解決理由を残す。独立分類をしなければ未実施と記す。同一人の修正後回答を初回の正答へ上書きしない。

観察中に実際の健康・被害の相談へ移った場合は、その詳細を記録票へ転記せず、課題を中断する。実際の摂食判断を求めない。個人の氏名・連絡先・診断・症状・服薬・病歴、実店の機密資料は本演習の記録項目にしない。
