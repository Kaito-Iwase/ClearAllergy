## 起動と終了

```powershell
node scripts/ingredient-change-trial.mjs --help
node scripts/ingredient-change-trial.mjs --serve --minutes 30
```

起動時に `http://127.0.0.1:<一時ポート>` とランダムtoken付き進行役URLを出力する。進行役URL/tokenは操作者へ配布せず、通常nav・HTML・通常state DTO・検証manifestには含めない。既定30分、`--minutes` は1–120の整数。Ctrl+Cまたは指定時間でサーバーを終了し、セッション内の全合成データとtokenの有効性を破棄する。タブの表示や既に出力した検証ファイルを自動削除する意味ではない。

事前に既存のアプリ依存とビルド済みCSSが必要。Turbopackの `.next/static/chunks` とwebpackの `.next/static/css` に対応し、必要なら `--assets-root <既存buildのルート>` を指定する。スクリプト自身はinstall/build/generateを行わない。元のCSSのファイル名とSHA256を出力する。

`--check` は既存の `PLAYWRIGHT_MODULE_PATH` と必要に応じた `BROWSER_EXECUTABLE` を指定して実行する。`--output <証拠出力先>` へJSONと画像を置く。外部アイコンフォントを読み込まず、既定では装飾glyphだけを省略する。取得済みの `material-symbols.css` / `material-symbols.woff2` がある場合、`--icons-root <そのディレクトリ>` でローカル配信できる。CSSのURLは同originの固定フォント一つに限定する。スクリプトはフォントを新規取得せず、使用したcacheのSHA256を残す。

## 架空データの固定定義

変更する料理IDは `trial-dish-one`、架空店舗IDは `trial-shop-f` とする。実DBのID・実在商品名を使わない。材料は既存の `ingredients` テキストと架空資料カードで表現し、新schemaにしない。

```text
架空店舗: 演習店 F
料理: 架空・きのこの小丼
レシピ R1: 米 / きのこ / ソースA / 白ごまの飾り
ソースA / A-1: 架空の小麦・大豆を使用、乳は原材料として不使用と明記
レシピ R2: 米 / きのこ / ソースB / 白ごまの飾り
ソースB / B-1: 架空の小麦・大豆・乳を使用と明記
工程カード K-?: 今回の資料では共用器具・交差接触は未確認
```

状態表は `ALLERGEN_MASTER` を基準に全件を作る。R1は小麦・大豆・ごまを `CONTAINS`、乳は `FREE`。R2は乳も `CONTAINS`。その他のマスター項目をFREEにする場合は「架空真値表で非使用と明示した条件」として設定し、記録欠損をFREEへ埋める実装と混ぜない。現在の実食品の事実ではない。B不完全版では乳を `UNKNOWN` とし、他の確認できた使用情報は消さない。

U04相当を含めるときだけ、変更しない補助データ「背景表示用の架空デザート」を追加できる。乳CONTAINSの公開登録から `storeHandledAllergenSlugs` を既存処理で導出し、小丼の乳FREEと別料理由来の補足を比較する。対象の材料変更は小丼一料理だけであり、このデザートの変更工数を測らない。

資料カードの製品識別・版は人が読んで選ぶ合成文字列。架空のバーコード認識、供給元API、AI解析、版の自動照合、在庫自動追跡を実装済みと見せない。

## 保存応答と画面の境界

料理編集には既存の `menuSaveResponseSchema` とCASの契約を満たす合成応答を使う。保存済み＋公開反映未完了は `publicRefreshPending` で分ける。競合409と不正200も、入力が保持されるかを見るための別条件にする。成功DTOを作るには #73/#74後の型・呼出元を再確認し、古い応答形を推測で使わない。

#73の店舗基本情報保存の3故障系を、MenuEditClientの合成応答だけで合格扱いにしない。必要なら店舗基本情報の実UIを使う技術fixtureを別で作り、演習の材料変更データと結果を分離する。#73の実ハンドラ・隔離実DB・ブラウザの証拠は実装PRの検証記録へ置く。

STOPのfixtureは未保存フォーム全量を送らないことを維持し、停止結果と食品記録の失効を独立に制御する。STOPした後に旧フォームをそのまま新CAS版へ結び直す代用品を作らない。

## 通信・保存・操作の条件

- loopbackのHTTPだけにbindし、外部公開しない。固定ポートの要否は既存fixtureと衝突しないよう後続実装で決める。
- ブラウザの外部リクエストを遮断し、保存先はfixture内の合成状態だけにする。画像・Clerk・Blob・実DBを読み書きしない。
- サーバー側でも任意URLのプロキシ機能、実APIへの転送を持たない。ブラウザ遮断だけで他プロセスの通信が止まるとは報告しない。
- 状態は一時プロセス内に保持する。実参加者の回答をアプリへ自動送信する解析・録画機能を増やさない。
- 操作者面で模擬だと分かる表示は維持する。進行役の操作パネルで正解・採点・資料の欠けを先に教えない。
- 通常state DTOはgeneration/menu/master/materials/publicVisible/listRowだけ。recipes、physical、inventory、providedBatch、scenario、answerNotes等はtoken付き進行役投影だけに返す。推測した `?facilitator=1` のHTML/stateやtokenなしの条件制御は403。tokenは公開アプリの権限ではなく、同じPC・OS・履歴・開発者ツールからの機密保護を保証しない。
- 開発者予行と自発回答観察を分ける。初回回答を記録する場合、進行役の全資料/採点票は別PCまたは進行役だけの紙で管理し、操作者と同じPC・ターミナル・ブラウザ履歴を共用しない。操作者の端末で進行役URLを開いてから返さない。loopbackを他PCへ公開する機能はないので、参加者実施の機材・資料授受・事前設定は別途整える。
- localStorageの個人設定は独立ブラウザcontextを使い、実ユーザーの設定を触らない。試験ごとに初期値と解除を記録する。
- `.next` の同時build/devを避ける。使うCSSが古ければ画面の版を混ぜない。fixtureの保存応答を実際の永続化と表示しない。
