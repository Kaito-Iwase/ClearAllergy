# 操作から保存・表示まで

[READMEへ](../../README.md) · [共通ルール](rules.md) · 次は[開発手順](development.md)

## ファイルの役割を先に理解する

| 場所・技術 | このアプリでの役割 |
| --- | --- |
| `app/` / Next.js App Router | URLとページを対応させる入口。丸括弧のフォルダは整理用でURLには含まれない |
| `features/` | 公開店舗、管理メニュー、店舗、認証、招待ごとの画面と処理 |
| `components/` | ヘッダーなど実際に共用している表示部品 |
| `lib/` | アレルゲン、権限、DB接続、画像などの共通処理 |
| `prisma/schema.prisma` | DBに何を保存し、どう関連づけるかの定義 |
| `prisma/migrations/` | DB構造やトリガーを順に変更する履歴 |
| `tests/` / `scripts/` | 自動テストと、環境準備・ブラウザ確認・運用のスクリプト |

Server Componentはサーバー上でデータ取得・画面生成を行うReact部品、Client Componentはブラウザで入力やクリックを扱う部品です。APIは画面などがHTTPで処理を呼ぶ窓口、Route Handlerはその要求を受けるNext.jsの入口です。ここでは多くのRoute HandlerがHono（HTTP処理をまとめるライブラリ）の実装へ転送します。PrismaはTypeScriptからDBを読み書きする道具です。

**ページの初期表示が必ず自分のAPIを呼ぶわけではありません。** 多くはServer ComponentがPrismaで直接取得し、必要なデータだけをClient Componentへ渡します。API一覧と具体的な入口は[変更対応表](change-map.md#apis)を使ってください。

<a id="public"></a>
## 店舗・メニューを見る処理

1. `app/(public)/shops/page.tsx` などが対応する `features/public/shops/server/` のページを呼ぶ。
2. ページが `readPublicDataOrFallback` の中でPrismaを使い、店舗・公開メニュー・品目マスタを取得する。認識したDB接続障害は、取得失敗を示すフラグと代替値に分けて返す。
3. [公開条件](rules.md#publication)で不完全なメニューを除く。状態を組み立てる際は有効な4状態以外を `UNKNOWN` に正規化し、公開APIも不正値を含むメニューを404にする。詳細では店舗IDとメニューIDの対応も照合する。対象なしの404とDB障害の案内を区別する。
4. 店舗内の他の公開可能メニューから補足情報を作り、登録状態と表示用の値を分ける。画像URLも表示可能なものに絞る。
5. 日付などをブラウザに渡せる形へ整え、一覧や詳細のClient Componentへ渡す。
6. ブラウザは検索語や端末のアレルゲン設定を使って表示を絞る。設定変更のたびにDBへ問い合わせる構成ではない。

公開メニューAPIも公開条件を検査しますが、ページとは別の入口です。APIテストの成功だけではページ側の取得処理を検証したことになりません。

公開店舗系ページには `force-static` と `revalidate = 60` があり、キャッシュ（過去の生成結果を再利用する仕組み）を使います。60秒ごとの定期更新や、保存後60秒以内の反映保証ではありません。変更APIは `lib/public-cache.ts` の関数で関連ページを再検証対象にし、別メニュー由来の補足も更新対象にします。外部からDBを直接変更するとこのAPI経由の無効化を通りません。実環境の反映時間は別途確認が必要です。

<a id="preferences"></a>
## 個人設定を適用する処理

1. `UserAllergenPreferenceClient` が `lib/public-allergen-preferences.ts` の購読処理を使い、保存済み設定を読む。
2. 未知の品目・重複・旧形式を正規化する。同じ品目が強調と非表示の両方なら非表示側を優先する。
3. 保存済み値と編集案を分け、個々の選択で編集案だけを変更する。
4. 適用時に `localStorage` へ全体を保存する。書込失敗は保存済み状態に反映しない。
5. 同じ画面と別タブの変更通知を受け、一覧・詳細が共通の確認対象を読む。編集中の別タブ変更には競合処理を挟む。

DB、Clerk、サーバー側のユーザープロフィールへの保存はありません。入力を変更する場合は選択UIだけでなく、正規化・購読・検索・結果表示も確認します。

<a id="mutation"></a>
## メニューを保存・公開する処理

1. 管理ページがClerkとDBから自店舗を解決し、既存値・品目マスタをフォームへ渡す。
2. フォームは名前や公開準備状況を確認し、必要なら見直し確認を表示する。
3. 新規は `POST /api/admin/menus`、編集は `PUT /api/admin/menus/[menuId]` へJSON（項目名と値で表すデータ）を送る。
4. APIが同一オリジン、ログイン、自店舗、ポートフォリオ更新許可を確認する。編集・削除時は既存メニューの取得と最終書き込みの両方をサーバーで解決した店舗IDで限定する。
5. 入力の型、価格、文字数、画像URL、品目を検証する。部分更新の状態は既存値へ統合し、公開条件を判定する。
6. トランザクション（複数のDB操作をまとめて成功・失敗させる単位）でメニューと品目別リンクを保存する。取得後に対象店舗が変わって最終書き込みが失敗した場合は404とし、先行したリンク削除を含めて巻き戻す。DBトリガーの追加防御もある。
7. 監査ログ、公開ページの再検証を行い、結果を返す。画面は成功時だけ保存後の遷移・状態更新を行う。

店舗情報もフォーム → APIの権限・入力検証 → DB更新 → 公開側の再検証 → 成功表示という順です。ただし店舗更新はフォーム全体を送る方式で、メニューの部分更新と同じ契約ではありません。

画像は先にアップロードAPI → Blobへの保存 → URL取得を行い、そのURLを店舗・メニュー保存へ渡します。DBとBlobを単一トランザクションにできているわけではありません。失敗・削除時の制約は[画像ルール](rules.md#images)を参照してください。

<a id="invitations"></a>
## ログイン・招待の処理

ログイン画面は補助APIで入力・回数を確認した後、Clerkで認証します。パスワード・二段階認証では `signIn.finalize()` でセッションを有効にしてから成功通知を送り、管理入口へ進みます。Googleログインのコールバックは、Clerkの読込完了と有効セッションを待って通知します。`/api/admin/auth/login` と `/api/admin/auth/sso` は補助・監査用で、独自セッションの発行APIではありません。

両補助APIは、本文解析より前に共通の回数制限を通します。成功通知は `lib/auth/auth-audit.ts` がサーバーのClerkセッションを検証し、既存アプリユーザーを読み取って監査記録に関連付けます。本文のメールや成功フラグだけで認証成功にしません。記録の意味、重複抑止と制限の範囲は[共通ルール](rules.md#audit)を参照してください。

招待作成では運営権限を確認し、入力・重複・店舗所有者を検査し、Clerkへ招待を作成して `AdminInvite` に記録します。新しい店舗名で招待する場合は非稼働の店舗を準備します。ClerkとDBは別サービスなので、片側失敗を含む補償処理も確認対象です。

受諾APIは、リクエストのメールや店舗IDではなくClerkの本人情報を使います。有効期限の処理後、該当メールの有効な `pending` 招待をDBでロックして取り出し、店舗所有者と既存ユーザーの競合を確認します。同一トランザクションでユーザー連携、店舗所有者設定・稼働化、招待の `accepted` 化を行います。競合は409などで返します。

招待の内部状態は `pending` / `accepted` / `revoked` / `expired` / `failed`。取消はDBで `pending` の行だけを `revoked` に変えてからClerkを取り消します。受諾と競合して既に `accepted` なら上書きせず409です。Clerkの取消が失敗すると502ですが、ローカルの受諾は止まっています。Clerk招待IDが残る `revoked` 行には取消再試行ボタンを表示し、成功後にIDを消します。

再送は旧Clerk招待を取り消した後、まだ `pending` で旧IDも一致する行のIDを消します。新Clerk招待の発行後、トランザクションで旧 `pending` を `revoked` にし、新しい `pending` 行を作成します。DBの競合・失敗時は新しいClerk招待の取消を試みます。旧IDを消した後の失敗では、Clerk招待IDがない `pending` 行が残る場合があり、再送で再試行できます。外部通信を待つ間ずっとDBトランザクションを保持する方式ではありません。

Clerkへの補償取消自体の失敗、外部成功後のDB更新失敗、通信結果が不明な場合は、自動処理だけで一致を保証できません。要求IDと操作分類を手掛かりに、権限のある運営者がClerkとDBを照合します。作成・再送・取消・受諾の業務監査はDB確定後に記録します。期限切れ処理は関連操作時の処理であり、定期ジョブがあると推測しないでください。

<a id="data"></a>
## DBのつながり

| モデル | 保存するもの・関連 |
| --- | --- |
| `User` | アプリ内ユーザー。Clerk ID、メール、移行互換用のパスワードハッシュ。通常認証はClerk |
| `Shop` | 店舗情報、稼働状態、所有者、画像設定。ユーザーとの関連は任意、一意 |
| `MenuItem` | 1店舗に属するメニュー。内容、公開状態、画像設定 |
| `Allergen` | 品目の識別名 `slug`、日本語・英語名、表示順 |
| `MenuItemAllergen` | メニュー×品目の中間表。組み合わせを一意にし、その状態を保存 |
| `AdminInvite` | 対象店舗、招待先、Clerk招待ID、期限、受諾・取消などの状態 |
| `AuditLog` | 操作者・対象・成功／失敗・日時などの管理操作記録 |

店舗削除はメニュー・招待へ、メニュー削除は品目リンクへ連鎖します。これは削除してよいという許可ではありません。DB削除とBlob上のファイル削除は別です。詳細な制約は `prisma/schema.prisma` と既存マイグレーションを確認してください。

招待のメール別・店舗別の `pending` 一意性は部分一意インデックス、公開内容が不完全なときの自動非公開はコミット時の制約トリガーでも守ります。これらはSQLマイグレーションにあるため、`schema.prisma` だけや `db push` で環境を再現できるとは限りません。実DB回帰は既存マイグレーションを適用した専用DBで確認します。詳細は[検証手順](development.md#browser)へまとめています。

<a id="observability"></a>
## 要求と障害を追う処理

`app/api/` の入口は `withRequestObservability` で包み、サーバー生成の要求IDと固定したルート名を処理へ引き継ぎます。完了時に `request_completed` と状態・処理時間を記録し、同じ要求IDを `X-Request-Id` で返します。`logOperationalError` は `operation_failed` と操作名、分類、許可したエラーコードを記録します。呼出先で内部エラーを認識した場合は、完了ログにもその分類を引き継ぎます。

DB接続障害、外部サービス失敗、業務上の入力・権限エラーを区別するための仕組みです。Honoの各APIには共通の `handleUnhandledApiError` を設定し、未捕捉例外も安全なログと汎用的な500へ変換します。Prismaの生のerror/warn出力は使わず、安全な項目だけを共通ロガーへ渡します。監査DBにも要求IDとルート名を付加しますが、業務監査と運用ログは保存先・目的が違います。[保存する情報の境界](rules.md#audit)を守って調査します。

ページ側では `instrumentation.ts` の `onRequestError` が、Node.js実行環境でNext.jsの捕捉した想定外例外を共通ロガーへ渡します。APIラッパーと同じ要求ID・完了時間が必ず付くわけではありません。`app/error.tsx` / `app/global-error.tsx` は利用者へ一般的な案内と再試行を表示し、生の例外文を表示しません。

ブラウザ内例外の外部収集、ClerkやBlob内部の処理すべての追跡は行いません。フレームワーク等の別のロガーまで同じ出力制限を保証するものでもありません。外部監視への通知、ログ保存期間、監査DBの保管方針、可用性の保証は別の運用設定です。

## 技術構成と選定記録

現行はNext.js 16.3.4、React 19系、TypeScript、Tailwind CSS、Hono、Clerk、Prisma 6系、PostgreSQL、Vercel Blobです。正確な解決バージョンは `package-lock.json` を優先します。Node.jsとnpmの開発基準は[開発手順](development.md#environment)へ集約しています。

ページの `params` / `searchParams` はPromiseとして受け取り、`await` して読みます。型確認に加え、buildが生成するNext.jsのページ型との整合性も検証します。

従来READMEには、Next.jsで公開・管理・APIを一緒に扱う、TypeScriptでデータ型を扱う、Tailwindで表示状態を調整する、Prismaで型とDBを対応させる、PostgreSQLで関連データを扱う、Clerkへ認証を委ねる、Blobへ画像を分離する、Vercelで配備するという選定意図が記録されていました。これは既存の説明の保存であり、今回比較実験をした結果ではありません。

Prisma設定依存の `deepmerge-ts` には限定overrideがあります。互換性の試験入口は変更対応表にあります。過去の脆弱性検査結果を現在の安全性の根拠にはしません。
