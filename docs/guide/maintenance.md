# 文書を変更と一緒に保守する

[READMEへ](../../README.md) · [変更対応表](change-map.md) · [AGENTS.md](../../AGENTS.md)

この手順は、文書作業だけでなくアプリコードの変更にも適用します。必要な文書更新が残っていれば、その作業を完了扱いにしません。文書を直しただけで実装・動作も検証済みとはしません。

## 変更前：根拠と範囲を分ける

1. AGENTS.md、Git状態、依頼・受け入れ条件を確認し、既存変更を保持する。
2. 変更対応表から関連仕様を読む。共通ルールの正本は [rules.md](rules.md)。表にない機能なら、実装を調べて説明先または未対応理由を表に追加する。
3. コード検索で入口の呼び出し元・共通関数・API（画面などから処理を呼び出す窓口）・DB（データベース）・テストを追う。表に載ったファイルだけで影響範囲が完結するとはみなさない。
4. **影響を受ける範囲**（挙動・データ・文書）、**実際に変更する範囲**（編集するファイル）、**確認のみの範囲**（検査するが編集しない箇所）を分けて伝える。依頼と無関係な修正を混ぜない。

根拠は次の区分で書きます。

| 区分 | 記録すること |
| --- | --- |
| 明示要件・承認済み方針 | 依頼や合意の内容・出典。見つからない承認を創作しない |
| 実装 | ファイルと関数・部品名、到達できる処理。古いコメントや到達しない分岐だけを仕様にしない |
| テスト定義 | どの条件を何で検査するか。モック・実DB・実ブラウザを区別 |
| 今回の実行結果 | 対象コミット、環境、コマンド、結果、件数、未実行理由。過去の成功を転記しない |
| 過去の記録・仮説・未確認 | 日付・当時の対象・未確認理由。現在も存在する問題か照合する |

実装と承認済み方針が食い違う場合は、双方の根拠と影響を[確認範囲・不一致](verification.md#issues)または作業報告へ記録します。動いているから正式仕様、という判断をしません。設計理由が分からなければ「理由未確認」とします。

<a id="update-map"></a>
## 変更時：同じ仕様を二重に管理しない

変更種別と文書の役割の対応はこの表を正本とし、具体的な機能・コード・API・DB・テストの入口は [change-map.md](change-map.md) だけで管理します。

実装担当が影響する説明・参照を同じ変更内で更新し、レビュー担当が差分から代表経路を追い、要件・実装・テストとの一致、更新内容または更新不要の理由を確認します。変更のたびに、すべての文書を編集する必要はありません。

| 変わる内容・残す資料 | 対応する文書と更新範囲 |
| --- | --- |
| 製品の目的・利用境界・主機能・デモ・起動の要約・読む順番 | [README](../../README.md) の該当説明・入口 |
| 操作・画面・入力・表示・画面遷移 | [product.md](product.md) の該当機能 |
| 共通の状態の意味・公開条件・権限 | [rules.md](rules.md) を正本として更新。各ページに条件全文を複製しない |
| ディレクトリ構成・責務・依存・処理順・データ関連 | [architecture.md](architecture.md) の該当説明。図が説明する経路も変わる場合は編集用drawioと表示用SVGを併せて照合する |
| 起動・環境・操作/検証コマンド・テスト・運用手順 | [development.md](development.md)。`package.json` の実行コマンド定義（`scripts`）と呼び出すスクリプト、Windowsの実行方法・前提・副作用・成功判定を照合する |
| ページ・機能・URL・API・実装/テストのパスや参照先 | [change-map.md](change-map.md)、該当本文の相対リンク、索引。単なる移動で変わらない仕様本文は書き換えない |
| 新しい調査・未採用案・設計判断 | `docs/research/` に出典・日付・適用限界・状態を残し、[研究索引](../research/README.md)から案内する。採用判断と実装の確認なしに現行ガイドへ昇格させない |
| 長期保存する検証・障害対応の実行証拠 | `docs/verification/` に対象SHA（コミットの識別値）・環境・コマンド・結果・未確認を残す。[verification.md](verification.md)は現在の制約・不一致と詳細結果への入口を更新する。過去の証拠の日付・対象・結果を現在へ読み替えない |
| 作業ルール・必須コマンド・正本への参照 | [AGENTS.md](../../AGENTS.md) の必要な指示だけ。仕様全文や変更履歴は増やさない |

仕様・説明・参照が変わらない文書は確認だけに留めます。更新文書・確認した章と変更との対応、更新不要の理由は[報告の詳細](#reporting)へまとめます。再利用する詳しい実行証拠は日付付き文書へ残し、同じ内容をチャット・PR・Issueへ重複して貼り付けません。

- ファイル追加・移動・改名・削除で参照が変わったら、対応表、本文のパス、相互リンク、READMEの読む順番も確認する。
- 現行説明は古い記述への追記だけで済ませず、本文を整合させる。調査案を承認済み仕様や実装済み機能にしない。過去の証拠は日付・対象・当時の結果を保ち、後続の訂正や検証は別の時点として記録する。古い資料を無断で大量削除しない。
- AGENTS.mdは重要ルール・コマンド・参照先が変わったときだけ更新する。作業の変更履歴は蓄積しない。

初心者向けとAI向けに別仕様を作らず、本文は目的→操作→内部処理の順で書き、対応表を調査の入口にします。専門用語は初出で短く説明します。ソースコード例は必要な場合だけ、抜粋か独立実行かを明記して全行を説明します。手順には環境・前提・コマンドの意味・成功判定・失敗時の確認先を付けます。

## 完了前のチェックリスト

- [ ] 依頼・承認済み方針、実装、関連テスト、本文の意味が一致している。不一致は未解決として記録した。
- [ ] 追加・変更・削除したページと主要機能が対応表に反映され、説明先または未対応理由がある。
- [ ] READMEの入口から、主要操作、処理、起動、テストへ進める。
- [ ] 相対リンクの対象と見出し、コードパス、関数名が実在する。記載したコマンドを現在のscripts・実行手順と照合し、未実行は理由を残した。Git管理されないローカル資料を必須の参照先にしていない。
- [ ] 代表的な変更依頼を選び、関連仕様・実装・テスト・更新文書へ到達できる。共通ルールを各ページに複製していない。
- [ ] 必要な検証を実行し、未実施は理由を付けた。実DB・外部サービスへの副作用と接続先を事前に確認した。
- [ ] 秘密情報・実認証情報・個人情報・実データを追加していない。意図しない生成物もない。
- [ ] `git diff --check`、差分、`git status --short` を確認した。必要な文書更新の残りはない。

文書専用チェックのnpmスクリプトはありません。既存の [PRテンプレート](../../.github/pull_request_template.md) の詳細内の「文書・後続作業」で更新文書または更新不要の理由を示し、このチェックリストを作業の完了条件として使います。新たなCI・フックの導入は別提案です。

参照確認は既存ツールで行えます。以下はリポジトリルートのPowerShellで使う独立コマンドです。

```powershell
rg --files app features lib tests scripts prisma .github
rg -n 'getMenuPublishValidationErrors|isMenuPublishable' app features lib tests
git diff --check
git status --short
```

1行目は候補ファイルの棚卸し、2行目は公開判定の定義・呼出先を調べる例、3行目は差分の空白エラー検査、4行目は変更範囲の確認です。`rg`が使えない環境では追跡一覧に`git ls-files`、本文検索にPowerShellの`Select-String`を使います。検索だけでMarkdownリンクが有効と確認したことにはなりません。本文のリンク先・アンカーも開いて照合します。

## 報告の書き方

チャット・PR・Issueコメントは、同じ順番で読めるようにします。まず普段の判断に必要な短い入口を置き、詳しい調査用の情報へつなぎます。

1. **結果と現在地**：何の問題がどう変わったか。実装、検証、PR公開、マージ、配備のうち確認できた段階を示す。
2. **判断・次の操作**：ユーザーの操作が必要か、次は誰が何をするか。ユーザー判断が必要なときは、判断対象・推奨案・影響を示す。許可済みの作業やエージェントが解決できる技術問題を問い直さない。
3. **確認と証拠**：今回の主な確認結果と、必要なら詳細へのリンク。通常は入口全体で4〜8行を目安にし、小変更は短い一段の報告で足りる。

必須検証の失敗・未実施、未解決の重要リスク、判断待ちは入口から見えるようにします。行数は上限ではありません。ローカルPASSを本番確認や食品の安全性へ広げず、部分完了を全体完了と呼びません。現在の判断に関係しない一般的な未確認事項は、毎回列挙せず詳細へまとめます。

実コマンド・件数・対象SHA・環境・文書更新/不要理由・未実施理由・レビュー・残課題は、既存reportや検証記録、PRの `<details>` に保持します。短い作業は本文内で済ませ、新しい報告ファイルやテンプレートの全項目の埋め戻しを義務にしません。参照先があれば重複転記せず、今回の対象と一致する証拠を指します。ローカルファイルを参照できないGitHub上の読者には、PR本文の詳細かアクセスできる記録を用意します。

Issueのassessment markerとJSONは機械用の現行形式を保ち、その**前**に必要な短い説明を置きます。markerの後のJSONを折りたたみで囲むと既存parserが読めないため、変更しません。

例（書式例であり、実際の検証結果ではありません）:

> 表示の不具合を修正しました。ローカル検証は通過、PRはレビュー待ちです。
>
> あなたの操作は今は不要です。次はエージェントがPRのCI結果を確認します。
>
> 詳細：対象PRの検証記録。

進捗では作業コマンドを逐次実況せず、変わったこと・新しく分かったこと・次に解消する不確実性を伝えます。理解に必要な説明を単に短縮する運用ではなく、読む順番と置き場所のルールです。設計根拠と採用しなかった案は[比較記録](../research/engineering/output-clarity-20261114.md)を参照してください。
