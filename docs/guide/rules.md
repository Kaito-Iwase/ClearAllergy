# 共通ルール：状態・公開・権限

[READMEへ](../../README.md) · [操作とページ](product.md) · 次は[内部処理](architecture.md)

この文書が共通仕様の説明先です。ページ別の文書はここを参照し、状態表や公開条件を複製しません。根拠は[変更対応表](change-map.md#cross-cutting)から追えます。以下の実装説明を、未承認の仕様変更を正当化する根拠にはしません。

<a id="allergens"></a>
## 品目、保存状態、表示上の分類は別物

「品目」は卵・乳などの対象、「状態」はそのメニューに対する登録内容です。現行の `ALLERGEN_MASTER` は29品目。`lib/allergens.ts` は品目を9品目の「特定原材料」と20品目の「特定原材料に準ずるもの」に分けています。これは**現在のアプリ内分類**の説明であり、最新の法令への適合を確認した記述ではありません。件数を増減する変更では、定義だけでなくDB（データベース）のマスタ、固定件数の検証、マイグレーション、テストも調べます。

DBの `AllergenStatus` は4状態です。

公開側ではまとまりごとに「店舗が登録した内容」を示し、状態ラベルに登録情報という語を毎回繰り返しません。`FREE` は無彩色で示し、食品安全の保証ではない旨を一覧のFREEカードと詳細の説明に残します。色だけで状態を表現しません。2026-10-07の利用者承認による読みやすさの変更であり、保存状態、公開条件、除外条件の変更ではありません。

| 内部状態 `status` | 現在の基本表示 | 意味・注意 |
| --- | --- | --- |
| `CONTAINS` | 含む | そのメニューに含む登録 |
| `FREE` | 原材料に含まない | 店舗の登録内容。厨房の交差接触まで確認済みという意味ではない |
| `MAY_CONTAIN` | 含む可能性あり・要確認 | 不確実性を残した登録。仕入れ品の工場・ラインに関する注意情報や、店舗の共用器具・揚げ油等による混入の懸念を把握した場合も店舗が登録する。公開可能だが注意表示する |
| `UNKNOWN` | 公開側は未入力・未確認、管理側は未設定 | 信頼できる判断が入力されていない |

レコード欠損は表示・公開判定で `UNKNOWN` に補完します。DBの初期値も `UNKNOWN` です。保存済みの値を表示へ組み立てる共通処理も、有効な4状態以外は `UNKNOWN` として扱い、公開判定から除外します。`null`、空欄、不正値を `FREE` にしません。API（画面などから処理を呼び出す窓口）への入力は従来どおり不正な状態値や知らない品目を拒否します。これはDB上で不正値が実際に保存できることを示すものではありません。

工場・ライン等の注意情報を登録する場合は、対象品目・理由・仕入先の元の注意内容を既存の注意書きに残します。工場と製造ラインを区別し、メーカーの注意表示を含有の確認結果へ置き換えません。資料や確認が不足して判断できない場合は `UNKNOWN` を維持します。注意書きへの入力だけで状態は変わりません。原材料情報と厨房の交差接触についての情報は分けて確認します。

画面上の `effectiveRisk` は、保存状態に同じ店舗の別の公開登録を加味した**導出値**です。`FREE` の品目が別の公開可能メニューで `CONTAINS` なら `STORE_HANDLED` となり、別登録に含む情報がある旨を補足します。`CONTAINS`、`MAY_CONTAIN`、`UNKNOWN` は元の意味を保持します。`STORE_HANDLED` をDBの状態として保存しません。厨房を調査した結果でもありません。

利用者の「含む可能性があるものを除外・強調」は、ONの場合に登録MAY_CONTAINとFREE＋STORE_HANDLEDにも各品目の注目・除外設定を適用します。CONTAINSへの適用は常時です。MAY_CONTAINの注意情報はOFFでも保持し、UNKNOWN・欠損をFREEにしません。「別メニューに含む」の短ラベルと、その根拠が別の公開メニュー登録である補足を、原材料の状態と分けます。検索・除外で補足元を隠しても情報を失わず、非公開・公開条件を満たさないメニューを根拠にしません。詳細の直URLは情報を表示し、除外設定一致を案内します。

選択品目の結果では含む・可能性あり・店舗内の補足・未設定を隠しません。全選択が確認条件を満たさない限り、問題がないと受け取れる要約にしません。内部の見た目用分類に `safe` という名前が残っていても、食品安全の保証という意味ではありません。

利用者設定がない店舗内メニューカードでは、特定原材料を主な確認対象にします。確認対象に「特定原材料」を明記し、品目名と件数をこの分類で集計します。その他の品目に含む・可能性あり・未入力があれば、同じカード内の「その他のアレルゲン」で別に表示します。別メニュー由来の補足は店舗共通欄に1度表示し、原材料登録の状態へ混ぜません。特定原材料のマスタや登録の欠損は判定対象から外さず `UNKNOWN` とします。設定なしだけを理由に「含まない」とは判定しません。設定がある場合は注目・除外の選択品目で判定します。2026-10-07の利用者依頼による表示対象の変更であり、全品目の公開条件や登録状態は変更しません。

<a id="publication"></a>
## メニューの公開と公開側の取得

この作業ブランチは2026-10-21の承認による二段階公開へ変更しています。本番反映済みという意味ではありません。[判断理由・未確定事項](../research/product/two-step-publication-decision-20261021.md)と[検証記録](../verification/two-step-publication-20261021.md)を参照してください。既存未解決の明示解除もユーザーが暫定承認しました。現在は実装・検証中です。本番への反映は別承認です。

1. 名前が空でない。
2. DBのアレルゲンマスタがコードの品目集合と日本語名に一致し、欠損・余分・重複がない。件数はマスタ定義から導出する。
3. 現行マスタ全品目の状態が入力され、`UNKNOWN` やリンク欠損がない。`MAY_CONTAIN` は許可する。
4. 保存済みの現行食品版に対応した別の公開操作があり、保持された最新の食品確認記録に未解決事項がないか、その記録を対象とする現行食品版の明示解除記録がある。

1〜3は `getMenuPublishValidationErrors` / `isMenuPublishable`、4の版一致は `isMenuPublicationCurrent` で確認します。DBの `ca_require_menu_publication` は対応する公開操作または移行で保持した実在の旧記録も検証します。`reviewedFoodVersion` の一致を新しい公開操作の代わりにはしません。

新規は非公開で保存し、同じページで保存済み内容を見直して別に「この内容で公開」を押します。確認欄の「保存」は既に完了した非公開保存の確認を閉じる操作で、自動公開や追加保存をしません。未設定は名前・件数を表示して公開を止め、入力し直して再保存します。名前・説明・カテゴリ・原材料・注意書き・食品画像・所属店舗・品目別状態、マスタの品目・名称が変わると食品版が進み、公開の版対応と公開フラグを解除します。編集画面の手動の食品変更申告欄は一時撤去しています。同じ文字列のまま仕入れ仕様・代替・工程などが変わった場合は画面では検知できないため、手動で公開停止し、登録内容を見直します。APIの `foodChangeReported:true` による食品版更新・非公開化は保持します。以前の文字列に戻しても旧確認は復活しません。価格・画像構図だけの変更は食品版と現在の公開状態を維持します。

食品変更と公開を同じ要求へ入れても、その保存では公開しません。通常の再公開は `expectedVersion` と `publicationAction:"publish"` で、保存済みの最新版に対して行います。所有権・Origin・競合409・未設定拒否を維持します。旧 `foodReview` payload、POSTでの公開、非公開メニューへの旧 `isPublished:true` だけの要求は400で明示拒否します。既に公開中の価格等の更新で `isPublished:true` を送る旧要求は継続できます。

公開操作は操作者・実際の記録時刻・保存済み食品版を `MenuPublicationConfirmation` に追記します。食品資料を照合した時刻・根拠・安全性を作りません。長文入力の形式的負担に対する確認品質の効果は未検証であるため、必須フォームを外し、古い食品版の流用防止を独立した状態管理へ移しています。公開操作は食品安全の保証ではありません。

以前の `MenuFoodReview` は履歴として保持し、編集画面で直近5件と当時の内容を閲覧できます。既存の根拠・範囲・確認日時・記録日時・操作者・未解決事項を更新・削除しません。`CONTAINS` / `MAY_CONTAIN` を `FREE` へ変換しません。未解決を材料変更や通常の公開操作で黙って解除しません。店舗担当者は表示した未解決に実際に対応してから、別の「この内容は解消した」を操作します。旧記録を変更せず、解除対象ID・保存済み食品版・実操作者・実際の操作日時・未解決本文を `MenuFoodIssueResolution` に追記します。解除しても非公開のままです。その後に別の「公開する」を行い、UNKNOWN等の通常条件を再検査します。食品変更や最新未解決の更新では以前の解除を流用しません。 本番の該当データの有無は未照会です。

新しい `20261021000000_two_step_publication` と後続 `20261021010000_food_issue_resolution` を追加しています。前者は、適用時に既に公開中で、現行食品版に対応する実在の最新記録があり未解決のないメニューだけを旧記録IDで引き継ぎます。非公開の下書きは自動公開しません。新しい公開操作の履歴や食品根拠・確認時刻を補完しません。旧migrationは書き換えません。コードとDB制約の整合変更なので、新旧サーバー混在のままの切替は未検証です。本番への適用は別途承認・手順確認が必要です。

公開フラグ `isPublished=true` だけで公開側へ渡しません。公開一覧・詳細・メニューAPIは稼働店舗 `isActive=true` とフラグを確認し、取得後にも入力条件と公開の版対応を検査します。公開可能メニューが0件の店舗詳細は404、店舗一覧には1件以上の店舗だけを渡します。

既存の `20260622000000_auto_unpublish_incomplete_menus` による不完全データの自動非公開も維持します。DBトリガーはアプリの検証の代わりではなく、コードだけで稼働DBへの適用状況は断定できません。公開読取は食品本体・状態・マスタ・補足を同じDB時点から取得します。訂正前に開始した取得と訂正後の新しい取得は区別し、開いた画面への自動配送や一律の日数による失効は追加していません。

過去の確認履歴と新しい公開操作は追記式です。メニュー・店舗の削除では関連履歴も連鎖削除されるため永久保存の監査ではありません。公開画面の一般的な更新日時は食品根拠の確認日時ではありません。

店舗内の取扱い補足は、引き続き他の公開可能メニューだけを根拠とします。補足元が停止すると補足も消える場合があり、補足の不在は店舗内にその品目がないことを証明しません。公開条件や注意文の緩和には製品方針の明示的な判断が必要です。

食品情報を載せる `/shops`・店舗詳細・メニュー詳細は、アクセスごとにDBを読み、サーバーのページキャッシュから過去の公開情報を返さない設定です。非公開時はnot-found（対象が見つからないことを示す）画面にしますが、Next.jsのストリーミング開始後の判定ではHTTP 200のままnot-found画面とnoindex（検索エンジンへの非掲載指定）を返す場合があります。公開メニューAPIは404です。既に開いた画面・戻る操作・オフライン画面へ訂正を自動配送する機能はありません。公開停止のDB確定と、あらゆる閲覧者への訂正到達は別です。

<a id="ownership"></a>
## 認証・所有権・運営権限

**認証**は誰がログインしているかの確認、**認可**はその人が対象を操作できるかの確認です。

- Clerkのサーバー側セッション → `User.clerkUserId` → `Shop.ownerClerkUserId` と `isActive` の順に店舗を解決します。通常のユーザー取得は読み取り専用です。ログイン確認だけで旧メールアドレスのユーザーを自動連携しません。
- 管理メニューの取得・更新・削除はメニューIDと解決済み店舗IDで絞ります。PUT/DELETEは事前取得に加えて、トランザクション内の最終更新・削除も両IDで限定します。事前取得後に店舗が変わった対象は404とし、リンク更新も巻き戻します。リクエスト本文の `shopId` や所有者フラグを信用しません。管理ページは未認証でログインへ、店舗未割当なら登録入口へ移動します。APIでは未認証401、店舗なし403、他店舗の対象404を使います。
- 運営管理者はClerkの `publicMetadata.role === "admin"` で確認します。招待管理権限と、個別店舗の編集権限は同一ではありません。管理者ロールだけで任意店舗のメニュー更新APIが使えるわけではありません。
- `PORTFOLIO_MODE=true` では更新に追加制限があります。運営管理者、許可したアプリユーザーIDなどは更新可。許可判定には設定値だけでなくコード内の既定IDも含まれます。これは所有権確認を省略する許可ではありません。
- `proxy.ts` は管理・認証ルートでClerk状態を扱う入口です。これだけで対象データの所有権を保証しません。ページ・APIのサーバー側チェックも必要です。
- 管理更新では[同一オリジンと回数制限](#request-security)も確認します。どちらもClerk認証や店舗所有権の代わりではありません。

自己登録は `getAdminRegistrationMode()` が常に `disabled` を返します。旧環境変数を `open` に変えても再開しません。店舗作成・割当は運営の招待と受諾を通します。招待受諾だけは、Clerkから取得したメールと有効招待を照合して、未連携の既存ユーザーを連携する処理があります。通常ログインとの違いに注意してください。

現行DBは `Shop.userId` と `ownerClerkUserId` がそれぞれ一意で、1店舗の複数担当者を表すメンバー表はありません。「招待」は複数管理者の追加機能を保証しません。

<a id="request-security"></a>
## 管理APIの同一オリジンと回数制限

管理更新の共通処理は、`Origin` のスキーム・ホスト・ポートを、要求URLのスキームと標準 `Host` ヘッダー（なければ要求URLのホスト）から作ったオリジンと比較します。欠落、不正値、別スキーム・別ポート・別ホストは403です。`GET` / `HEAD` / `OPTIONS` はこの更新用チェックの対象外です。`X-Forwarded-Host` / `X-Forwarded-Proto` を追加の許可先として扱いません。

この境界は、配備先のプロキシが公開 `Host` を保ち、Next.jsへ渡すプロトコル情報を正規化することを前提とします。単体テストでヘッダーの組み合わせを確認しても、Vercelや別のプロキシの実設定まで確認済みにはなりません。配備先を変更する際は正規のHTTPS要求が通り、不正オリジンが拒否されることを確認します。

ログイン・SSO（外部アカウントによるログイン）補助APIは、同一オリジン確認後、本文解析・認証照会・監査DB書込より前に、両API共通でIP当たり10分30要求を制限します。不正JSONや成功・失敗通知も対象です。パスワード事前確認には追加でIP当たり10分10回・メール当たり5回、SSO開始にはIP当たり10分10回の制限があります。超過は429と `Retry-After` を返し、拒否自体を認証監査DBへ大量に書き込みません。これはClerkへ直接送る認証要求の制御ではありません。

IPの取得は、Vercelが設定する `VERCEL=1` の環境で、上書きされた `X-Forwarded-For` の先頭が有効なIPの場合に限ります。それ以外は `unknown` の共通枠を使います。自己申告ヘッダーを信頼するために、この環境変数を他の配備先で設定してはいけません。制限用のIP・メール・セッション識別子はハッシュ化したキーとしてプロセス内メモリに保持します。期限切れの掃除と最大10,000キーの上限があり、満杯なら新しいキーも拒否します。複数プロセス間で共有されず、再起動でも消えるため、分散した濫用への完全な防御ではありません。

<a id="images"></a>
## 画像・入力・エラーの共通境界

画像APIは認証、店舗所有権、更新許可を確認し、JPEG・PNG・WebP・GIF・AVIF、5MiB以下を受け付けます。申告されたMIMEタイプ（ファイル形式を示す値）とサイズに加え、先頭最大4KiBの形式署名を照合し、空ファイルや形式の不一致を拒否します。画像全体のデコードやマルウェア検査を保証する仕組みではありません。Vercel Blob（画像ファイルの保存サービス）へアップロードし、DBにはURLと表示設定を保存します。配備基盤のリクエスト容量制限は別にあるため、アプリの上限内でも転送が成功するとは限りません。

URLはHTTPS、許可したBlobストア、自店舗の保存パスを検証します。枠は正方形／横長、表示は `cover`（枠を埋める）／`contain`（全体を収める）、拡大率50〜250%、位置0〜100%の範囲です。既存URLも表示前に検証し、不許可なら画像として使いません。アップロード成功とDB保存成功は別段階で、古い画像の自動回収は未整備です。

外部入力はAPIでZod（入力の型と条件を検査するライブラリ）や既存の検証関数へ通します。画面の必須表示だけでは保証しません。APIのエラー形式は統一されておらず、主に `error` / `message` を画面の共通処理で取り出します。すべての障害が503になるわけではありません。契約を変更する場合は呼び出し元も調べます。

共通レスポンスには `X-Content-Type-Options: nosniff` と `Referrer-Policy: strict-origin-when-cross-origin`、管理ページには `X-Frame-Options: SAMEORIGIN` を設定します。これらは入力検証や認可の代わりではありません。CSP（読み込めるリソース等を制限する仕組み）やHSTS（HTTPSの利用をブラウザに求める仕組み）の一律設定は追加していません。

<a id="audit"></a>
## 認証監査と運用ログ

`AuditLog` は認証・招待・店舗・メニュー等の管理操作を記録します。食品の確認履歴を利用者へ提供する機能とは別です。認証成功の通知は、サーバーでClerkのユーザーIDとセッションIDを検証できた場合だけ `auth_session_verified` として保存します。検証できなければ401で、成功記録を作りません。

クライアントの開始・失敗通知は `source=client_report` と区別し、認証成功の証拠にしません。`entrypoint=password/google` は通知を受けた経路を表し、実際の認証方式や最初の認証時刻を証明しません。以前の `auth_login_success` 等の記録を、現在の検証方式による記録と読み替えないでください。

同一セッションの成功通知はプロセス内で10分間重複を抑えます。サーバー間で一度だけの記録を保証するものではありません。監査保存はベストエフォートで、記録失敗時も確定済みの業務更新を戻しません。監査の完全性や長期保管・通知を保証する仕組みとは区別します。

監査DBには必要な操作者・対象IDを保持し、メタデータは状態・変更項目名・固定理由コードなどの許可した項目だけを保存します。必要なClerk操作者IDはサーバーセッション由来に限ります。新規の監査書込にはIP、メール、入力本文、任意のエラー文、画像パス、生のセッションIDを追加しません。過去データの削除や匿名化を実施したという意味ではありません。

運用ログは `lib/observability.ts` が要求ID、固定したルート名、結果、HTTP状態、処理時間、エラー分類などをJSON（項目名と値で表すデータ形式）で出力します。ユーザーID、実URLのクエリ・対象ID、認証情報、エラー本文・スタックをそのまま出力しません。APIレスポンスの `X-Request-Id` を使って対応するログを探します。適用範囲と障害調査は[内部処理](architecture.md#observability)と[開発手順](development.md#operations)を参照してください。秘密情報・個人情報・実データを文書や検証ログへ写さず、監査DBの内容も無条件に貼り付けないでください。
